```luau
--!strict
export type CardId = number
export type Rank = number -- 1..config.ranks for naturals; JOKER_RANK (0) for a joker
export type SeatId = number
export type PlayerId = number
export type JokerMode = "Wild" | "Blocker"
export type RemoveCause = "Completed" | "Disconnected" | "Benched"

export type EngineConfig = {
	ranks: number,
	jokers: number,
	jokerMode: JokerMode,
	-- The anti-livelock valve (02-CONTEXT.md amendment A7), implemented in plan 02-13 and wired by
	-- plan 02-07. A VALUE, never a module constant, for the same reason `jokerMode` is one: the
	-- sweep must run both positions in one process, and the valve's own mutation proof is a run
	-- with it off. The shipped configuration sets it true and plan 02-11 asserts that.
	antiLivelockValve: boolean,
}

-- The valve's whole state. Carried on State so a round is reproducible from its seed alone.
-- NOT hashed by Invariants.hash and NOT inspected by Invariants.check: it is bookkeeping about the
-- trajectory, not part of the table. If it were hashed, no state could ever repeat and the valve
-- could never fire.
export type ValveState = {
	rng: any, -- an Rng, derived in Engine.newRound so valve draws never perturb the deal
	actionsSinceProgress: number, -- reset by a completion or a removal
	armed: boolean, -- true once actionsSinceProgress passes VALVE_ARM_ACTIONS_PER_SEAT * liveCount
	seen: { [string]: true }, -- hashes observed since the last completion, removal or firing
	seenCount: number,
	firings: number, -- the first-class metric: a pool whose valve fires often is a bad pool
	seenResets: number, -- times VALVE_SEEN_CAP forced a restart of the window
	-- Exactly one valve entry point is called per SUCCESSFUL apply and none on a rejection, so plan
	-- 02-08's fuzz suite asserts observations == acceptedActions. Without it the valve could be
	-- skipped inside a conditional and read green, which is the defect class Phase 1 found twice.
	observations: number,
}

export type Seat = {
	id: SeatId,
	playerId: PlayerId,
	live: boolean,
	hand: { CardId },
	inbox: { CardId }, -- FIFO: index 1 is the front (next draw), #inbox is the tail
	next: SeatId,
	prev: SeatId,
}

export type Counters = {
	rankInPlay: { number }, -- rankInPlay[r] = copies of natural rank r in hands+inboxes
	jokersInPlay: number,
	cnt: { number }, -- cnt[a + 1] = how many natural ranks have exactly a copies in play, a in 0..4
	completions: number,
	churnRemovals: number, -- removals with cause ~= "Completed"; each adds 4 to circulation
}

export type State = {
	config: EngineConfig,
	seatCount: number, -- m0: seats dealt at round start = (players in round) - 1
	totalCards: number, -- T = 4 * ranks + jokers
	rankOf: { Rank }, -- rankOf[cardId]; the shuffled deck permutation, re-randomised per round
	seats: { Seat },
	liveCount: number,
	head: SeatId, -- any live seat, used as the ring entry point; 0 when the ring is empty
	retired: { CardId }, -- cards retired by completions
	terminal: { CardId }, -- cards held when the ring emptied (research 7.3); never destroyed
	counters: Counters,
	valve: ValveState,
}

export type Intent =
	{ kind: "Draw", seat: SeatId }
	| { kind: "Pass", seat: SeatId, cardId: CardId }
	| { kind: "Remove", seat: SeatId, cause: RemoveCause }

export type Reject =
	"UnknownSeat" | "SeatNotLive" | "UnknownCard" | "NotYourCard" | "HandNotFour" | "HandNotFive" | "InboxEmpty"

export type Event =
	{ kind: "Drew", seat: SeatId, cardId: CardId }
	| { kind: "Passed", seat: SeatId, to: SeatId, cardId: CardId }
	| { kind: "Completed", seat: SeatId, rank: Rank, retired: { CardId }, fifth: CardId }
	| { kind: "SeatRemoved", seat: SeatId, cause: RemoveCause, routedTo: SeatId?, cards: number }
	-- The valve fired: the engine forced this seat to pass this card. `lap` is
	-- `actionsSinceProgress` at the firing, so the metric is in the event stream and not only in a
	-- counter. It carries NO hash: the hash encodes every hand, and an event may cross the network
	-- boundary in Phase 4 (CLAUDE.md rule 3).
	| { kind: "ValveForcedPass", seat: SeatId, cardId: CardId, to: SeatId, lap: number }

export type ApplyResult = { ok: boolean, events: { Event }, reject: Reject? }

return {
	JOKER_RANK = 0,
	HAND_SIZE = 4, -- a resting hand; the pile "locks at 5" is just: draw only when #hand == HAND_SIZE
	MAX_HAND = 5,
	MAX_JOKERS = 2, -- research 3.3: at j <= 2 the all-joker set is unreachable and the completing rank is unique
	MAX_DEAL_ATTEMPTS = 64, -- research 10: ~50 standard deviations above the measured max of 4
	-- The valve starts hashing only after a table has gone this many actions per live seat with no
	-- completion and no removal (48 * liveCount = 432 actions at 9 seats, roughly 22s of play).
	-- It is a COST gate and nothing else: hashing every draw costs ~2us per action, which is fine
	-- for a sweep but would blow the CI subset's 4.0s budget, while a healthy 9-seat round is
	-- ~250 actions and so never arms. The only behavioural effect is that a cycle is detected at
	-- most one lap later than it could have been, because a cycle repeats forever until broken.
	VALVE_ARM_ACTIONS_PER_SEAT = 48,
	-- Bound on the valve's seen-set so a pathological round cannot grow memory without limit.
	-- A cycle shorter than this is still caught; passing it clears the window and counts a reset.
	VALVE_SEEN_CAP = 4096,
}
```

Create `src/server/engine/Invariants.luau`. It requires only `./Types`.

**`circulation(state)`** — sum over LIVE seats of `#seat.inbox + (#seat.hand - Types.HAND_SIZE)`.
Return 0 when `liveCount == 0`.

**`expectedCirculation(state)`** — `4 * (state.config.ranks - state.seatCount) + state.config.jokers
+ 4 * state.counters.churnRemovals`. Research §4.1: draw, pass and completion are all net zero;
only a non-completing removal moves it, and always by exactly +4.

**`satisfiable(state)`** — O(1), from the histogram, never a search:
- Wild mode: `true` iff `sum over a from max(1, 4 - jokersInPlay) to 4 of cnt[a + 1] > 0`
- Blocker mode: `true` iff `cnt[5] > 0` (some rank still has all 4 copies in play)
Return `true` when `liveCount == 0` (the round is over; there is nothing left to satisfy).

**`hash(state)`** — a canonical string: `head`, then for each seat index 1..#seats in order, `live`,
the hand sorted ascending, and the inbox **in FIFO order (not sorted)**. Hash NOTHING else: not
`counters`, not `valve`, not `rankOf`. This is load-bearing twice over — the valve (plan 02-13)
decides "this whole-table state has repeated" from exactly this string, so a hash that included a
monotonically increasing counter would make every state unique and the valve could never fire. Separate fields with
characters that cannot appear in a number (`|`, `,`, `/`). The inbox order must matter and the hand
order must not — the simulator's cycle detection (research §11.4) and the fuzz suite's
"state unchanged after a rejection" assertion are both built on this one function.

**`check(state)`** — returns `(ok, violationName)`. The violation names are a LOCKED vocabulary AND
a LOCKED ORDER; tests assert the exact string, so never reword one and **never reorder the list**:

| order | name | condition |
|---|---|---|
| 1 | `"hand-size"` | some live seat has `#hand` outside {4, 5} |
| 2 | `"ring-links"` | some live seat's `next` or `prev` is not a live seat, or `head` is not live while `liveCount >= 1` |
| 3 | `"liveness"` | `circulation >= 1` and `liveCount >= 1` but no live seat has a legal action (`#hand == 5`, or `#hand == 4` and `#inbox >= 1`) |
| 4 | `"circulation"` | `liveCount >= 1` and `circulation(state) ~= expectedCirculation(state)` |
| 5 | `"partition-count"` | `#hands + #inboxes + #retired + #terminal ~= state.totalCards` |
| 6 | `"partition-identity"` | scanning all four buckets, some card ID in `1..totalCards` does not appear exactly once |
| 7 | `"counters-rankInPlay"` | `rankInPlay` / `jokersInPlay` recomputed by scanning hands+inboxes disagrees with `state.counters` |
| 8 | `"counters-histogram"` | `cnt` recomputed from the scanned `rankInPlay` disagrees with `state.counters.cnt` |
| 9 | `"unsatisfiable"` | `liveCount >= 1` and `satisfiable(state) == false` |

Checks 4 and 7 are the whole point of the module and must be written so they CAN fail: **derive one
side independently.** Recompute hand/inbox contents and rank counts by walking the actual seat
containers and compare against `state.counters`. Research Pitfall 4: a conservation check whose two
sides are produced by the same helper is green forever, and Phase 1 verification found two checks
exactly like that. Do not add a cached `circulation` field to `State` and compare it with itself.

`partition-identity` costs a scratch table of `totalCards` entries. Research §4.2 benchmarked the
full identity scan at 343,502 actions/s versus 595,017 for counters only — 1.7x, which is why there
is no tiering: `check` always does everything, and callers that cannot afford it call `circulation`
and `satisfiable` directly.

**Do not reorder the table to make a test green.** `circulation` (4) precedes `unsatisfiable` (9)
deliberately: a card that vanished is a conservation bug and must be reported as one. If
`unsatisfiable` came first, every genuine conservation bug would surface as a stall statistic in the
simulator instead of as an error, which is the opposite of the two-sided-derivation design in this
module. Plans 02-06 and 02-09 carry the same warning, and both assert `satisfiable(state)` directly
rather than asking `check` for a name it is not going to reach.

`liveCount == 0` is the ring-emptied case (research §7.3). In that state circulation is 0 by
definition, so checks 3, 4 and 9 are skipped and the partition identity is the only live proof that
the terminal cards were accounted for rather than destroyed. Write that as a comment at the skip.

No `error()` calls: `check` reports, it does not throw. The caller decides whether a violation is
fatal.

   for `k` in {1, 2} and `j` in {0, 1, 2}, in both joker modes.
2. `"circulation equals 4*(ranks-seats)+jokers at the deal"` — assert `circulation(state)` equals
   `Invariants.expectedCirculation(state)` equals `4*k + j` for each of those cells. This is
   CARD-04: the circulating supply is a constant of the pool, not an accident of play.
3. `"a dropped card on pass fails the circulation check"` — remove one ID from the dealer's inbox
   (do not touch counters) and assert `check` returns `(false, "circulation")`.
4. `"a duplicated card on draw fails the circulation check"` — append a copy of an existing in-play
   ID to a hand and assert `(false, "circulation")`.
5. `"an extra retired ID fails the partition count"` — append `totalCards + 1` to `state.retired`
   and assert `(false, "partition-count")`. This mutation leaves circulation untouched, which is
   why `partition-count` has to exist separately.
6. `"a swapped card fails the partition identity"` — replace a hand card with a duplicate of
   another in-play ID, then repair `counters` so the counter checks pass. Assert
   `(false, "partition-identity")`. Add a comment: this is the exact bug counters cannot see
   (research §4.2), and it is why the identity scan exists.
7. `"a 6-card hand fails the hand-size check"` — assert `(false, "hand-size")`.
8. `"a broken ring link fails the ring-links check"` — point a live seat's `next` at a dead seat and
   assert `(false, "ring-links")`.
9. `"desynced rank counters fail counters-rankInPlay"` — decrement `counters.rankInPlay[1]` only,
   assert `(false, "counters-rankInPlay")`. This is the Pitfall 4 proof: the two sides of the check
   are genuinely independent and CAN disagree.
10. `"a dead multiset is reported unsatisfiable"` — this case must reach violation **9** of the
    locked order, so the state has to be clean on violations 1 through 8 first. The naive mutation
    (delete cards from play) drops circulation and `check` returns `"circulation"` — violation 4
    precedes violation 9 — so it never reaches `unsatisfiable` at all. **Do not reorder the
    violation list to fix that.** Build a conservation-clean fixture instead, using this identity,
    which falls straight out of `expectedCirculation`:

    > `circulation == expectedCirculation` holds iff `#retired + #terminal == 4 * (seatCount - liveCount - churnRemovals)`
    > — i.e. **four cards out of play per completed (non-churn) removal, and no more.**

    So: `ranks = 4`, `jokers = 0`, `seatCount = 3`, `totalCards = 16`, `expectedCirculation = 4`.
    Mark seat 3 as a COMPLETED removal (`live = false`, empty hand and inbox, `churnRemovals = 0`),
    giving `liveCount = 2` and a retirement budget of exactly 4 cards. Put in `retired` **one copy
    of each of the four ranks** rather than four copies of one rank, leaving every rank at 3 copies
    in play. Give the two live seats 4 cards each plus 2 inbox cards each, so circulation is 4 and
    at least one seat has a legal action (otherwise violation 3, `liveness`, fires first).
    Recompute `counters` by scanning. Then assert, in this order:
    - `check(state)` returns `(false, "unsatisfiable")` — every one of violations 1 to 8 is clean
    - `satisfiable(state) == false`
    Then add one joker into play (raise `jokers` to 1, `totalCards` to 17, and hand the joker to a
    live seat's inbox — which also adds 1 to both circulation and `expectedCirculation`, so the
    fixture stays clean) and assert `satisfiable` flips to `true` in Wild mode and stays `false` in
    Blocker mode. The mode asymmetry is CARD-10 versus CARD-12 at the predicate level.

    Add this comment: a retirement of one card from each of four ranks is **not reachable by legal
    play** — a real completion retires four of ONE rank, which is precisely why research §3.1 finds
    structural unsatisfiability unreachable while Rule 8 holds. The fixture is allowed to build it
    because `check` must detect a dead multiset wherever it arises; the claim that play cannot
    produce one is asserted empirically by plan 02-06's destroy mutation and plan 02-08's fuzz run,
    not by making this predicate unreachable.
11. `"satisfiability is an O(1) histogram read, not a scan"` — assert `cnt` sums to `ranks` on a
    clean state, and that moving four cards of one rank to `retired` shifts exactly one histogram
    bucket.
12. `"the canonical hash sees an inbox reorder and ignores a hand reorder"` — two structurally equal
    states hash equal; swapping two cards within one hand hashes equal; swapping the first two cards
    of an inbox hashes DIFFERENT; moving one card from an inbox to a hand hashes different.
    The simulator's cycle detection and the fuzz suite's "state unchanged" assertion both depend on
    this, so a hash that cannot see an inbox reorder would silently disable both.
13. `"the canonical hash ignores counters, the valve record and rankOf"` — take a hash, then
    separately: bump `counters.completions`, bump `valve.actionsSinceProgress`, bump
    `valve.firings`, swap two entries of `rankOf`. Assert the hash is IDENTICAL after each. This is
    the valve's load-bearing precondition (plan 02-13): the valve fires when a whole-table state
    repeats, and anything monotonic inside the hash would make every state unique, so the valve
    would never fire and amendment A7's mechanism would be silently vacuous — the exact defect class
    Phase 1 verification found twice.

Every case uses `t.equal`/`t.falsy` on the violation name, never a bare `t.falsy(ok)`.
