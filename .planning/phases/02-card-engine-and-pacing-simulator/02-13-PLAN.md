<objective>
The anti-livelock safety valve (02-CONTEXT.md amendment **A7**): a pure engine module that notices
the whole table has returned to a state it has already been in, with no completion since, and forces
one uniformly random pass from the seat that just drew. Plus the deterministic cycle fixture that
proves it fires, which plans 02-07, 02-09 and 02-11 all reuse.

Purpose: a purely greedy table livelocks. Measured at N=10 over 4,000 rounds per cell, the stall rate
with no valve is **0.275% at k=1,j=1**, **0.250% at k=2,j=1** and **21.6% at k=2,j=2**. With the valve
it is **0.000%**, **0.000%** and **0.025%**, while the valve fires in only ~0.25% of rounds at j=1.
The mechanism amendment A1 originally relied on — the AFK auto-pass — cannot carry that load: its
firing rate is exactly the tail of the reaction-time distribution past the pass deadline (2.86% at
1.0s, 0.21% at 1.5s, 0.019% at 2.0s, ~0 at 5s), and a 1.5-second pass deadline is not an AFK
mechanic. At any deadline a real AFK feature would use, the auto-pass fires essentially never and the
gate silently reduces to pure greedy. So the fix belongs in the engine, where it is deterministic and
testable, rather than in an unverifiable claim about players.

**State the guarantee honestly and do not overstate it.** A7's phrase "zero stall becomes a theorem
about the engine" is stronger than the measurement supports: at k=2,j=2 the valve-on stall rate is
0.025%, not 0. The claim this plan licenses is: *the valve eliminates observed stalls for the
selected pool, demonstrated at the full round count, and its firing rate is itself a pool quality
signal.* Zero stalls is a measured property of a chosen configuration, never an unconditional
property of the engine. Any plan text, comment or report section that says otherwise is wrong.

Output: `Valve.luau`, `tests/harness/Livelock.luau`, and a spec in which the valve has been shown
both to fire and to be necessary.
</objective>

```luau
-- src/server/engine/Valve.luau
-- A fresh valve state. `seed` comes from Engine.newRound as rng:nextUint(), so valve draws never
-- perturb the deal and the deal never perturbs the valve, while both stay functions of one seed.
new: (seed: number) -> Types.ValveState

-- Called by Engine.apply at the end of a successful apply that produced a Completed or SeatRemoved
-- event. The state space changed, so the SEEN WINDOW restarts. `armed` is deliberately left
-- untouched -- see task 1 for why clearing `seen` is soundness and un-arming is only cost.
afterProgress: (state: Types.State) -> ()

-- Called by Engine.apply at the end of every OTHER successful apply. `drewAtSeat` is the seat that
-- just drew (so it now holds MAX_HAND cards and must pass next), or nil when the action was a pass.
-- Returns the card ID the engine must force that seat to pass, or nil for "do nothing".
afterAction: (state: Types.State, drewAtSeat: Types.SeatId?) -> Types.CardId?
```

**Exactly one of `afterProgress` and `afterAction` is called per successful `apply`, and neither is
called on a rejection.** Both bump `state.valve.observations`, so plan 02-08's fuzz suite can assert
`observations == acceptedActions` — the same trick as its `checksRun >= totalActions` assertion, and
the only way to catch the valve being accidentally skipped inside a conditional.

**Locked firing rule.** The valve fires when ALL of these hold:
1. `state.config.antiLivelockValve` is true
2. `drewAtSeat ~= nil` — the observation point is immediately after a non-completing draw, which is
   the only instant at which a known seat holds `MAX_HAND` and therefore has a legal pass
3. `state.valve.armed`
4. `Invariants.hash(state)` is already in `state.valve.seen`

**Locked choice rule.** `AUTO_PASS_SELECTION`-style and for the same reason: take the drawing seat's
card IDs whose rank is not `JOKER_RANK`, sorted ascending, and pick index `rng:nextInt(1, #naturals)`.
If the hand holds no natural (unreachable at `j <= 2`, where a 5-card hand holds at least 3 naturals)
fall back to the lowest card ID in the hand.

Create `src/server/engine/Valve.luau`, requiring exactly `./Types`, `./Invariants` and `./Rng`.

**`new(seed)`** — `{ rng = Rng.new(seed), actionsSinceProgress = 0, armed = false, seen = {},
seenCount = 0, firings = 0, seenResets = 0, observations = 0 }`.

**`afterProgress(state)`** — `observations += 1`; `actionsSinceProgress = 0`; `seen = {}`;
`seenCount = 0`. **Do NOT touch `armed`.** Comment both halves of the reason, because they are not
the same kind of reason:
- Clearing `seen` is required for **soundness**: a completion or a removal changes the state space,
  so a hash recorded before it can never legitimately recur afterwards, and keeping it would make the
  valve fire on a state that is not a cycle at all (research §11.4 requires exactly this reset).
- Un-arming is only a **cost** choice, and here it is the wrong one. Arming already costs 48 actions
  per live seat with *no progress at all*; a round that has paid that once has demonstrated it needs
  watching, and re-arming from scratch after every completion would let the same cycle run another
  full arm period. That is the identical argument this module makes a few lines below for leaving
  `armed` true after a FIRING — the two sites must agree or the module contradicts itself.
- There is no cost downside for healthy play: a healthy round never arms in the first place (a
  9-seat round is ~250 actions against a 432-action threshold), so only a round that has already
  proven pathological keeps hashing. It also makes plan 02-09's `valveArmed` metric mean "this round
  ever armed" rather than "the valve happened to be armed when the last action landed", which is how
  that metric is read.

**`afterAction(state, drewAtSeat)`** — in this order:
1. `observations += 1`; `actionsSinceProgress += 1`.
2. `armed = armed or actionsSinceProgress >= Types.VALVE_ARM_ACTIONS_PER_SEAT * state.liveCount`.
   Comment: the arm gate is a COST gate and nothing else. Hashing on every draw costs roughly 2
   microseconds per action — fine for a sweep, but it would blow the CI subset's wall-time budget
   (plan 02-09 derives that budget from measured throughput; do NOT quote a number here, because a
   stale budget baked into a shipped source comment is how a correct comment becomes a wrong one),
   while a healthy 9-seat round is ~250 actions and so never arms (48 x 9 = 432). The only behavioural effect
   is that a cycle is detected at most one lap later than it could have been, because a cycle repeats
   forever until something breaks it.
3. Return `nil` immediately if `state.config.antiLivelockValve` is false, if `drewAtSeat == nil`, or
   if `armed` is false. **Do not hash in any of those cases** — that is the whole point of step 2.
4. `local h = Invariants.hash(state)`.
5. If `seen[h] == nil`: `seen[h] = true`; `seenCount += 1`; if `seenCount > Types.VALVE_SEEN_CAP`
   then `seen = {}`, `seenCount = 0`, `seenResets += 1`; return `nil`.
6. Otherwise the whole table has returned to a state it has already been in, with no completion and
   no removal in between (because `afterProgress` empties the window). Fire:
   - `firings += 1`
   - `seen = {}`, `seenCount = 0` — the forced pass changes the trajectory, so the window restarts.
     Leave `armed` true: this round has already shown it needs watching, and re-arming from scratch
     would let the same cycle run another full arm period.
   - choose the card by the locked choice rule in `<interfaces>` and return it

**Why the drawing seat and not "a random seat".** At the observation point that seat holds
`MAX_HAND` cards, so it is the only seat with a provably legal pass, and it is about to pass anyway —
the valve changes WHICH card leaves, not whether a pass happens. The reference prototype that
produced the 0.25%-fires / 0.000%-stalls numbers also fired on the drawing seat immediately after a
non-completing draw, so the numbers ARE comparable — but record this as **this plan's choice, held
constant so the comparison is meaningful**, not as a rule amendment A7 or its correction state.
Neither document names a firing point. The distinction is load-bearing for plan 02-14: if its
measured firing rate diverges from the reference, the arm gate is only ONE of three candidate causes,
the others being this firing point and the naturals-only choice rule below. Attributing a divergence
to the arm gate alone would close the investigation on the wrong suspect.

**Why uniformly random, and why naturals only.** The deviation is the mechanism: research §3.6
measured that the stall rate collapses as soon as a trace of passes are cards a greedy player would
not have chosen, and that randomising the greedy TIE-BREAK is not enough (44.7% to 26.3%) because the
cycle is created by "never pass from your largest group". A valve that passed the "best" card to pass
would be re-deriving the player's own greedy choice and the deviation would be exactly zero — the
same trap R4 closes for the shipped auto-pass. Naturals only, because in Wild mode a joker is the
most valuable card in the hand and dumping it is a bigger disturbance than the mechanism needs. The
reference prototype did pick uniformly from the naturals, so the measured numbers are comparable —
but again, this is **this plan's choice, held constant so the comparison is meaningful**, and not a
rule amendment A7 states. Keep it so the numbers stay comparable; if plan 02-14 finds a divergence in
the firing rate, this rule and the firing point above are candidate causes alongside the arm gate.

**Honest-guarantee comment, verbatim in the header.** The valve eliminated observed stalls at
k=1,j=1 and k=2,j=1 (0 of 4,000 rounds each) while firing in ~0.25% of rounds; at k=2,j=2 it reduced
stalls from 21.6% to 0.025% but did NOT reach zero, and it fired in 21.6% of rounds there. So: the
valve is demonstrated to eliminate stalls for a GOOD pool, and its firing rate is a better pool
discriminator than its stall rate — a configuration whose valve fires in one round in five is a bad
configuration even when its stall rate looks fine. **Claim only what was measured: observed stalls
eliminated for a good pool, demonstrated rather than guaranteed.** The acceptance criterion greps the
written module for the phrases an overstatement would use, so paraphrase the prohibition rather than
quoting it into a comment.

No `error()` calls in the firing path: the valve reports by returning, like `Invariants.check`. Do
`error()` on a malformed call — `drewAtSeat` naming a seat that is not live or does not hold
`MAX_HAND` cards is a caller bug in `Engine.apply` and must be loud, because silently returning nil
would make the mechanism look vacuous rather than broken.
