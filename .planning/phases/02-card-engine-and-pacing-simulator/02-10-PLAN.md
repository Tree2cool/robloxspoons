<objective>
The full sweep: one committed script that searches the pool grid and the auto-pass timeout, then
confirms the selected configuration at the locked 10,000 rounds per (N, pool) cell, and writes a
committed report plus a machine-readable data file.

Purpose: CONTEXT locks "10,000 rounds per (N, pool config), and the bar is ZERO stalls" and locks
the full sweep as a manual/nightly run whose output is committed as a report. The grid this phase
must cover is larger than it was when that number was set — two joker modes, two churn variants, and
(per plan 02-09) a sweep over the auto-pass timeout that makes amendment A1's mechanism visible — so
this plan runs it in **two stages**: a coarse search at 1,000 rounds per cell to locate the passing
region, then a confirmation of the selected configuration at the full 10,000. The locked bar is
applied where it matters, to the configuration that ships.
**What this plan does and does not do.** It gets the owner's answer to the two questions that decide
what the sweep searches, then builds and smoke-tests the sweep CLI. **Plan 02-14 runs it** — the real
run is tens of minutes and belongs in its own plan so the long wait is not entangled with writing the
tool, and so a broken tool fails in three seconds instead of after forty minutes. Plan 02-11 then
makes the decision against the committed artefacts.

Output: `scripts/sim/sweep.luau` and its smoke test.
</objective>

Create `scripts/sim/sweep.luau`, requiring `./Simulator`, `@lune/fs`, `@lune/process` and
`@lune/serde`.

**CLI:** `lune run scripts/sim/sweep.luau -- [--stage search|confirm|mechanism|triage|both] [--rounds N] [--out DIR] [--pool kJ] [--seeds LIST] [--cap N]`
- `--stage` defaults to `both` (meaning `search` then `confirm` then `mechanism`)
- `--rounds` overrides the per-cell round count (the smoke test uses 5; omit for the real run)
- `--out` defaults to `.planning/phases/02-card-engine-and-pacing-simulator`
- `--pool` (confirm stage only) forces the configuration to confirm, as `k,j,mode,autoPassSeconds`
- `--seeds` and `--cap` are used only by `--stage triage`: re-run the named seeds at a raised action
  cap to separate a cap artefact from a true residual livelock
- an unknown argument must print `unknown argument: X` and `process.exit(1)`, matching
  `tests/run.luau`'s rule that a typo must not look green

**Stage `search` — locate the passing region.** 1,000 rounds per cell (research measured 144,000
rounds across 18 cells x 8 N with 0 stalls at this depth, so 1,000 is a sound search depth):
- `k` in {0, 1, 2}, `j` in {0, 1, 2} — nine pools, of which `k=0,j=0` returns `DeadPool` from
  `Simulator.runRound` and is reported, not skipped (amendment A5)
- `autoPassSeconds` from `AUTO_PASS_CANDIDATES`, the list the owner approved in task 1 (the
  recommended default is {1.5, 3.0, 5.0, 8.0, math.huge}). `math.huge` disables the auto-pass
  entirely, which with the valve also disabled is the pure-greedy worst case the report must show
- `antiLivelockValve = true` for every search cell. The valve-disabled cells are the separate
  **mechanism stage** below, so the search grid does not double in size for evidence that only needs
  to exist at a few points
- `N` in {3, 6, 10} — the minimum roster, a middle and the cap
- `jokerMode` in {`Wild`, `Blocker`}, `churn` in {false, true}
- `identityCheck = false` (counters only: research §11.1 measured 1,904 rounds/s for counters versus
  1,099 with the full scan, and plan 02-08's fuzz suite is where the identity scan earns its cost)

**Stage `mechanism` — the evidence that the valve is load-bearing, and the auto-pass probe.** Small
and cheap, and it is what `Simulator.evaluateMechanisms` reads:
- for every pool with `k >= 1`, one cell at `N = 10`, Wild, `churn = false`,
  `antiLivelockValve = false`, `autoPassSeconds = math.huge`, **4,000 rounds**, Solvability mode —
  the valve-disabled twin. Expected stall rates: ~0.275% at k=1,j=1, ~0.250% at k=2,j=1, ~21.6% at
  k=2,j=2. At 4,000 rounds a 0.25% rate expects ~10 stalls, which is why the round count here is
  4,000 and not 1,000: the twin has to be visibly non-zero or `"valve-not-load-bearing"` fires.
- one auto-pass PROBE cell at `autoPassSeconds = 1.0`, `N = 10`, valve on, 1,000 rounds, Pacing mode.
  Expected `autoPassRate` ~2.86%. This exists because at a realistic shipped deadline the auto-pass
  correctly fires almost never, so its mechanism check has to be a probe rather than a bar on the
  gated cells.
Emit these cells into the same JSON table, flagged `role = "mechanism"`, so the report can show them
and `evaluateMechanisms` can find them.

**Stage `triage` — separate a cap artefact from a residual livelock.** For each seed given in
`--seeds`, re-run `runRound` with `actionCap` raised to `--cap` (default: ten times
`SOLVABILITY_ACTION_CAP`) and classify the result as `CapArtifact` when it then clears, or
`ResidualLivelock` when it still does not. **This stage exists because the one measured valve-on
residual — 0.025% at k=2,j=2, one round in 4,000 — was observed under a 20,000-action cap, and which
of the two it is decides whether the report's honest claim is "zero stalls" or "zero stalls for the
selected pool".** Plan 02-14 runs it on every `capArtifactCandidates` seed the confirm stage
produces. It is cheap: a handful of seeds at ten times the cap.

**Stage `confirm` — apply the locked bar.** For the configuration chosen by the search (or forced
with `--pool`): **10,000 rounds per cell**, `N` = 3 through 10 (all eight), `jokerMode` in
{`Wild`, `Blocker`}, `churn` in {false, true} = 32 cells, 320,000 rounds, `antiLivelockValve = true`,
`identityCheck = false`. Plus **4 valve-disabled twin cells** at the selected pool, `N = 10`, both
joker modes and both churn variants, at 10,000 rounds each: at a ~0.25% stall rate that expects ~25
stalls per cell, which is a solid non-flaky proof rather than the ~1 stall 500 rounds would give.
This is where CONTEXT's "10,000 rounds per (N, pool config), and the bar is ZERO stalls" is applied,
and it is applied to the configuration that ships. Record in the report that the search stage ran at
1,000 rounds and is a search rather than a gate.

**Selection rule — implement it exactly as stated here.** It is CONTEXT's locked rule as amended,
with one conflict resolved by PROJECT.md's authority (see the note below):
1. Consider only `k >= 1` (amendment A4: at `k = 0` the Blocker variant stalls up to 97.4% while
   Wild stalls 0%, so the joker flag would be a cliff rather than a flag, and CARD-12's "both
   variants behind a flag" would be false).
2. Consider only `j >= 1`. **PROJECT.md's Key Decisions table records "Jokers as wilds, gated on a
   solvability simulator — keeps the swings he wanted"**, so the existence of jokers is a decided
   design property, not an output of this sweep. CLAUDE.md states PROJECT.md wins over research and
   that decisions in its Key Decisions table are not to be re-opened. Research flagged this as
   OQ-C precisely because CONTEXT's "then fewest jokers" tiebreak, applied literally, returns `j = 0`
   and deletes them. The simulator's job for `j` is to **clear** the chosen count as safe, not to
   minimise it. `j = 0` is still measured and reported as a comparison.
3. Among the remaining cells, require every bar to pass in **both** joker modes and **both**
   churn variants (OQ-D: a flag that is only safe in one position is not a fallback).
4. Reject any cell failing the **valve-rate** bar (`valveFiringRate > 0.01`). Measured: good pools
   fire in 0.25-0.28% of rounds, k=2,j=2 fires in 21.6%. This bar catches what the stall bar cannot:
   k=2,j=2's valve-on stall rate is 0.025% and looks nearly fine while the engine is rescuing more
   than one round in five.
5. Choose the smallest passing pool: fewest extra ranks `k` first, then fewest jokers `j` subject to
   the floor the owner set in task 1. A larger pool is safer and flabbier; tightness is what makes
   the scramble tense. Tie-break between otherwise equal candidates on the **lower valve firing
   rate** — it is the most sensitive quality signal in the whole table.
6. **Choose `autoPassSeconds` by descending candidate order, with MARGIN, and with a defined
   fallback.** Walk `AUTO_PASS_CANDIDATES` from the largest finite value down and take the first that
   clears every bar at every N, in both joker modes and both churn variants, **with margin**:

   | bar | pass | pass WITH MARGIN |
   |-----|------|------------------|
   | stalls | `stallRate == 0` | `stallRate == 0` (there is no margin above zero) |
   | median-first | `<= 45s` | `<= 36s` (80% of the bar) |
   | p95-first | `<= 120s` | `<= 96s` (80% of the bar) |
   | occupancy | `>= 0.60` | `>= 0.66` (10% above the bar) |
   | valve-rate | `<= 0.01` | `<= 0.005` (half the bar) |

   If no candidate clears with margin, **descend the same list again accepting a bare pass**, take
   the first that clears, and set `selection.marginal = true` with the bars it only barely cleared
   named. If nothing clears even bare, exit non-zero. The first draft of this rule said "choose the
   largest value that still passes", which selects the most marginal configuration in the table by
   construction and leaves no path to a second choice when it later turns out to be too tight —
   exactly the kind of knife-edge selection that gets quietly relaxed later.
Emit the selection as a structured block in both outputs, including the named bar failures for every
rejected cell and the `marginal` flag with its reasons — a selection rule whose rejections are
invisible cannot be audited, and a marginal selection that does not say so is worse than a failure.
