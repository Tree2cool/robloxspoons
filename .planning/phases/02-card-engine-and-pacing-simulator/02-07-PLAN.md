<objective>
`Engine.apply`: the single mutation entry point. It validates an intent, calls the `Ring` and `Hand`
primitives, maintains the counters, and RETURNS its events instead of publishing them. Plus
`Engine.newRound`, which assembles a dealt state from a config, a seat order and a seed.

Purpose: research §9 names four properties that make this shape non-arbitrary. Events are returned
rather than published, so there is no place a handler could run mid-mutation — that is what makes
CLAUDE.md rule 6 structural rather than a convention. Every rejection carries its own code, because
a boolean return would make seven distinct bugs indistinguishable, and the house standard from Phase
1 is that a test asserts the reason: a gateway that rejected everything once passed a suite that
only checked "rejected". `Remove` is one intent with a cause, not three operations. And the intent
carries a stable card ID, never a target and never a hand index.
Output: `Engine.luau` and a spec with one case per reject code, each asserting the code and that the
state is byte-identical afterwards.
</objective>

```luau
-- Builds a fully dealt round. Errors (via Pool.deal) if the pool is invalid.
-- seatPlayerIds is already IN SEAT ORDER: index 1 is the dealer. SeatOrder (plan 02-02) produced it.
newRound: (config: Types.EngineConfig, seatPlayerIds: { Types.PlayerId }, rng: any) -> Types.State

-- The ONLY mutation entry point. Synchronous. No callbacks. Events are returned, never published.
apply: (state: Types.State, intent: Types.Intent) -> Types.ApplyResult
```

**Locked reject precedence** (tests assert the exact code, so a different order is a different
contract). First match wins:

| intent | order of checks |
|--------|-----------------|
| any | `UnknownSeat` (no such seat index) -> `SeatNotLive` (`live == false`) |
| `Draw` | ... -> `HandNotFour` (`#hand ~= 4`) -> `InboxEmpty` (`#inbox == 0`) |
| `Pass` | ... -> `UnknownCard` (`cardId` outside `1..totalCards`) -> `HandNotFive` (`#hand ~= 5`) -> `NotYourCard` (held by nobody, or by another seat) |
| `Remove` | ... (no further checks; the cause comes from outside) |

**Locked event order for a completing draw** — exactly three events from one `apply`, in this order:
`Drew` -> `Completed` -> `SeatRemoved{cause="Completed"}`. A non-completing draw emits only `Drew`.
A pass emits only `Passed`. A `Remove` intent emits only `SeatRemoved`.

**Validation, in the locked precedence from the `<interfaces>` block.** On any rejection return
`{ ok = false, events = {}, reject = <code> }` and **touch nothing**. Research's security domain
(V5) notes the two layers are not redundant: `src/shared/Net/Validate` rejects a malformed or NaN
payload shape and cannot know whether a hand holds a card; the engine rejects illegality and cannot
know a payload is NaN. So do not re-check types here beyond what legality needs, and do not assume
shape validation happened either — an out-of-range seat index is `UnknownSeat`, not an error.

`NotYourCard` covers two distinct situations and must cover both: the card is held by a different
seat, and the card is in play but in an inbox rather than any hand. Research §7.6: a card that was
auto-passed a moment before the intent arrived is no longer in the actor's hand, and that is a
rejection, not a crash. Also §7.6's other end: an intent whose ACTOR left between intent and
execution is `SeatNotLive` and must never be applied to a dead seat.

**`Draw` path** (the only place completion is checked — CLAUDE.md: four of a kind is checked only on
draw, because passing can only leave a subset of a hand that already had none):
1. `local cardId = Ring.draw(state, intent.seat)`; append `Drew` to `events`.
2. `local completion = Hand.detectCompletion(state.rankOf, seat.hand, state.config.jokerMode)`.
3. If `completion == nil`, return `{ ok = true, events = events }`.
4. Otherwise, in this order:
   a. move `completion.retired` out of the hand into `state.retired`, and decrement
      `counters.rankInPlay[completion.rank]` / `counters.jokersInPlay` and shift `counters.cnt`
      accordingly — retirement is the ONLY place in the engine where a card leaves play, apart from
      `Ring.removeSeat`'s terminal path (which `02-06-SUMMARY.md` confirms `removeSeat` owns). Do not
      update the same counter twice.
   b. `counters.completions += 1`
   c. append `Completed { seat, rank = completion.rank, retired = completion.retired, fifth = completion.fifth }`
   d. `local routedTo, cards = Ring.removeSeat(state, intent.seat, "Completed")`
   e. append `SeatRemoved { seat, cause = "Completed", routedTo = routedTo, cards = cards }`
5. The removal happens inside the SAME `apply` as the draw. CARD-07's wording is "detected on draw
   and immediately removes that player", and splitting it across two applies would make a window in
   which a completed seat is still passable-to.

**`Pass` path:** `local to = Ring.pass(state, intent.seat, intent.cardId)`; append
`Passed { seat, to, cardId }`. Never check for a completion here, and add the comment saying why
(passing can only leave a subset of a hand that already had none), so nobody later adds a
"defensive" check that would double-fire completions.

**`Remove` path:** `local routedTo, cards = Ring.removeSeat(state, intent.seat, intent.cause)`;
append `SeatRemoved`. One intent with a cause, not three operations: Phase 4's AFK bench and a
disconnect both route through here (CLAUDE.md rule 8).

no listener list and no clock. Header comment: events are RETURNED and the caller publishes them

makes the no-yield guarantee structural rather than conventional, and it is also why plan 02-03's
R3 ban is belt-and-braces rather than the only defence.

Do not call `Invariants.check` inside `apply`. The fuzz suite (plan 02-08) and the simulator (plan

checkable rather than assumed.
