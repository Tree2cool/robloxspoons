<objective>
The transport edit: one new server-to-client remote, the `Publisher` implementation, and the client
side that receives it.

Purpose: guard R4 confines `FireClient` and `FireAllClients` to `src/server/services/NetServer.luau`
and `FireServer` to `src/client/net/ClientNet.luau` (`zones.luau:44-46`, verified). That is why
plan 04-12's `CardTable` takes an **injected** `Publisher` and this is the only file that can
implement it. The whole of CARD-13's machine proof already exists in `privacy.spec`; what remains is
four lines of adapter plus one runtime guard, and this plan keeps it to that.

**V-12 closed in our favour** and the design should not work around the old caution: current primary
docs state RemoteEvents are reliable and ordered per connection per direction, **including across
different RemoteEvent instances**. So a second remote is free of ordering risk. Two caveats remain
and both shape this plan: the guarantee is of handler **start** order, not completion — so a handler
that yields can be overtaken — and undelivered messages are **lost on disconnect**, which is exactly
what plan 04-09's watchdog backstops.

Output: the Card remote, the `Publisher`, `ClientNet.onCard`, and the guard gate.
</objective>

`src/server/services/NetServer.luau` gains:

```luau
-- The card stream: ONE server-to-client RemoteEvent. V-12 (verified 2026-11-04) guarantees ordering
-- per connection per direction INCLUDING across different RemoteEvent instances, so a second remote
-- costs no ordering guarantee. Two caveats that shape the code: the guarantee is of handler START
-- order, not completion, and undelivered messages are LOST on disconnect.
export type Deps = {
	getPhase: () -> Gateway.RoundPhase,
	dispatch: (userId: number, intent: string, payload: unknown) -> (),
	onReject: (userId: number, intent: unknown, code: Gateway.Code) -> (),
	onError: (userId: number, intent: string, err: unknown) -> (),
	-- NEW: which userIds are currently seated, so toSeated has an audience. Supplied by plan
	-- 04-14's CardService from the CardTable roster; an empty list means "no round", and toSeated
	-- is then a no-op rather than an error.
	seatedUserIds: () -> { number },
}

export type NetServer = {
	gateway: Gateway.Gateway,
	remote: RemoteEvent,
	cardRemote: RemoteEvent,
	publisher: CardRouting.Publisher,   -- hand this straight to CardTable.new
	destroy: (self: NetServer) -> (),
}
```

**The `Publisher` implementation, exactly:**

| Method | Behaviour |
|---|---|
| `toPlayer(userId, kind, payload)` | look the `Player` up in the roster; if absent, **return silently** (they left between the decision and the send — not an error); else `cardRemote:FireClient(player, kind, payload)` |
| `toSeated(kind, payload)` | `CardRouting.assertPublic(kind)` **first**; then `FireClient` once per seated `Player` found in the roster |
| `toAll(kind, payload)` | `CardRouting.assertPublic(kind)` **first**; then `cardRemote:FireAllClients(kind, payload)` |

`assertPublic` throws on a private or unknown kind. That throw is **defence in depth**: plan
04-05's frozen `AUDIENCE` is the decision and `privacy.spec` is the proof, but a later edit that
routes a `Sync` through `toSeated` must fail loudly at the first attempt rather than leak quietly.

**Roster:** a `{ [number]: Player }` built from `Players.PlayerAdded` / already-present players, and
cleared in the **existing** `Players.PlayerRemoving` handler beside `gateway:forget(player.UserId)`.
Without the removal it leaks a `Player` reference for the life of the server.

**Parenting order, which is load-bearing (the existing `Intent` remote's own comment says so):**
create both remotes, connect every handler, **then** parent. A message arriving while no handler is
connected sits in a bounded queue and is then dropped with an error.

`src/client/net/ClientNet.luau` gains:

```luau
-- Pitfall 11: `WaitForChild` is a YIELD POINT. Both remotes are resolved ONCE at boot, before any
-- handler is connected, so no gameplay message can arrive at an unresolved remote. The receive
-- handler must stay SYNCHRONOUS and non-yielding: V-12 guarantees handler START order, so a
-- yielding handler can be overtaken and the client would fold events out of order.
ClientNet.resolve = function(): ()          -- idempotent; call once from Main.client before anything else
ClientNet.onCard = function(handler: (kind: string, payload: unknown) -> ()): RBXScriptConnection
```

`FireServer` stays in this file and nowhere else (R4). `ClientNet.send` keeps its current signature.
`onCard` must **error by name** if called before `resolve`, rather than lazily yielding inside a
`Connect` call — a lazy resolve here is exactly the Pitfall 11 defect.
</interfaces>
