<objective>
Two small pure cores that each close a known hole: the stall cue's own no-progress detector (D-20),
and the reject-log throttle that resolves `01-CONTEXT.md` D-22 without touching the gateway.

Purpose, D-20, and **this one is mandatory rather than stylistic.** Phase 2 verification replayed 15
residual stalled seeds. All ran **2,431-4,429 actions without clearing** against a healthy mean of
~380, and **3 of the 15 had the valve armed with ZERO firings**. The valve fires only on an *exact*
whole-table state repeat, so a stuck trajectory that never exactly repeats is invisible to it. A cue
keyed off valve events would therefore be silent in exactly the rounds that need it. The detector
here is keyed on accepted actions without progress, and the signature makes a valve event
**unfeedable** rather than merely discouraged.

Purpose, D-22 (flagged in Phase 1 for revisit "in Phase 4 or Phase 8", carried as a planner
decision): **keep the gateway's check order, charge no token on a wrong-phase rejection, and
throttle the log instead.** The decision and its trade-off are recorded in task 2.

Also in scope: the CARD-14 consequence of that decision. A gateway-level rejection never reaches the
card core, so its `seq` is never acked individually — the throttle's `note` return value is what
plan 04-14 uses to also push a `Sync` so the client's pending entry is resolved. Without it a
rate-limited tap leaves a card visibly gone forever, which is exactly the "visible glitch" success
criterion 2 forbids.

Output: `StallDetector.luau`, `RejectThrottle.luau` and their two gates.
</objective>

```luau
--!strict  -- StallDetector.luau

export type Command = { kind: "StallCue" } | { kind: "StallClear" }

export type Deps = {
	-- BOTH conditions must hold before the cue arms. See the header for the derivation.
	actionsPerSeat: number, -- 96 = 2 x the engine's VALVE_ARM_ACTIONS_PER_SEAT
	minDeci: number,        -- 450 (45 s)
	cueDeci: number,        -- 50 (show for 5 s)
	repeatDeci: number,     -- 300 (re-show every 30 s while stalled)
	onTelemetry: (name: string, data: { [string]: number }) -> (),
}

export type StallDetector = {
	-- Called after EVERY successful apply. There is deliberately NO event parameter: the only
	-- signal is "an action was accepted and the table did not progress". A valve event cannot be
	-- fed in because there is nowhere to put it (D-20).
	noteApply: (self: StallDetector, liveSeats: number, nowDeci: number) -> (),
	-- Called on a Completed or a SeatRemoved, and only on those. Resets the window.
	noteProgress: (self: StallDetector, nowDeci: number) -> (),
	tick: (self: StallDetector, nowDeci: number) -> { Command },
	isActive: (self: StallDetector) -> boolean,
	actionsSinceProgress: (self: StallDetector) -> number,
}

StallDetector.new = function(deps: Deps): StallDetector
```

**Arming rule, both conditions required:**
`actionsSinceProgress >= actionsPerSeat * liveSeatsAtLastApply` **AND**
`nowDeci - lastProgressDeci >= minDeci`.

**Emission rule:** on the tick where it first arms, emit `StallCue` and record `lastCueDeci`. While
armed, emit `StallCue` again every `repeatDeci`. On `noteProgress` while armed, clear and emit
`StallClear` on the next tick exactly once. `cueDeci` is carried for the client's display window and
is published, not acted on here.

**Telemetry (D-20's explicit requirement, so Phase 8 tunes on a signal rather than a guess):** emit
`onTelemetry("stall_armed", { actions = n, deci = elapsed, liveSeats = m })` on arming and
`onTelemetry("stall_cleared", { actions = n, deci = elapsed })` on clearing. Nothing else; this is
not a metrics framework.

**Out of boundary, recorded:** this detector never ends a round. Round-end conditions belong to
Phases 5 and 6 (D-20). It raises a cue and emits telemetry; that is all.

```luau
--!strict  -- RejectThrottle.luau

export type Decision = {
	log: boolean,      -- write the individual warn line
	summary: number?,  -- non-nil when a window just closed with this many suppressed rejections
	streak: number,    -- consecutive windows in which this user was rejected at least once
}

export type Deps = { logPerWindow: number, windowDeci: number }

export type RejectThrottle = {
	note: (self: RejectThrottle, userId: number, code: string, nowDeci: number) -> Decision,
	streakOf: (self: RejectThrottle, userId: number) -> number,
	forget: (self: RejectThrottle, userId: number) -> (),
}

RejectThrottle.new = function(deps: Deps): RejectThrottle
```

**Rules:** per user, keep `{ windowStartDeci, countInWindow, loggedInWindow, streak }`. On `note`:
if `nowDeci - windowStartDeci >= windowDeci`, close the window — `summary` is
`countInWindow - loggedInWindow` when that is `> 0`, otherwise `nil`; `streak` increments if the
closing window had any rejections and **resets to 0** if a window closes empty; then start a new
window. `log` is true while `loggedInWindow < logPerWindow`. `forget` drops the entry (wired to
`Players.PlayerRemoving`, beside the existing `gateway:forget`, so it cannot leak for the life of
the server).

`streakOf` exists for Phase 8 only — **this phase does not kick anybody.** Say so in the header, so
nobody later finds an unused accessor and either deletes it or acts on it.

> **`01-CONTEXT.md` D-22, reviewed in Phase 4: the gateway's check order is KEPT. A wrong-phase
> rejection charges no token. The log is throttled instead.**
>
> The order is `isKnown -> phase gate -> bucket -> validate -> dispatch`
> (`Gateway.luau:56-98`). Charging a token on a wrong-phase message would cost a bucket
> lookup/refill and would allocate a per-user per-intent entry on first use, buys an attacker

> rejection**, so a `WrongPhase` flood was a log-spam and CPU vector throttled only by the
> platform's ~500 requests/second/client ceiling. That is what this file removes.
>

> inside a flood. The window summary and the per-user streak are the compensation, and Phase 8 may
