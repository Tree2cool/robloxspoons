<objective>
The client assembly: the Roblox backend behind the control seam, the input layer, and the one file
that wires the reducer to the renderer.

Purpose: every decision this plan uses is already made and tested. The reducer is plan 04-09, the
copy is plan 04-11, the geometry is plan 04-08, the control ordering is plan 04-11's
`Controls.onLocalCompleted`. What is new is the Roblox surface, and the standard it has to meet is
that it adds **no decision of its own**.

Two things are load-bearing:

- **UX-02's client layers (c) and (d).** `GuiService.TouchControlsEnabled = false` removes the
  thumbstick *graphics* from under the left pile, and a `ContextActionService:BindActionAtPriority`
  handler returning `Sink` stops `Space` also jumping. **`GetControls()` is never called and
  `PlayerModule` is never required** — it is undocumented, has never been documented, and a staff
  release post says the legacy endpoints "may no longer exist", with the engine default flipping in
  **early 2027** and the legacy scripts removed **mid-2027**. Plan 04-11's scan over `src/` enforces
  this.
- **UX-04 / D-09.** Hints follow `UserInputService.LastInputTypeChanged` — the **last input actually
  used** — and switch instantly, with no fade, at any time including mid-round.
  `UserInputService.PreferredInput` exists and is newer, but reports the *anticipated* primary input,
  which is a different question; it may seed the initial value and nothing more.

**D-08: the keyboard and the gamepad are additive.** The pointer path is the guaranteed one. Nothing
in this plan may become the only way to do anything, and the gamepad column has a recorded fallback
because its device behaviour is **V-27, unverified**.

Output: `CardControls.luau`, `CardInput.luau`, `CardClient.luau`, the booted `Main.client.luau`, and
an extended discipline gate.
</objective>

**Recorded, not fixed:** three community reports describe re-enable problems — a key held during the
disabled period not resuming until released (2024-04), a stuck jump button and dead thumbstick after
re-enabling on touch (2025-06), and a frozen jump button after `TouchControlsEnabled = false`
immediately following a jump (2024-01). None was re-tested here and all three bear directly on D-30.
**If the stuck-touch case reproduces in M-11, the recorded fallback is to re-assert by toggling
`TouchControlsEnabled` false then true on the next frame** — a recorded fallback, not a first resort,
and it must not be implemented speculatively.

```luau
--!strict  -- src/client/ui/CardClient.luau
-- THE ONE WIRING FILE. It owns the reducer, the HUD, the hand, the piles, the strip, the controls
-- and the input, and it is the only place they know about each other. Everything it does is plumbing:
-- any `if` that decides a game outcome belongs in src/shared/Card/.

```

**Message dispatch, through the single `ClientNet.onCard` handler. The handler must be synchronous
and must not yield** (Pitfall 11: V-12 guarantees handler **start** order, so a yielding handler can
be overtaken and the client would fold events out of order):

| Kind | Action |
|---|---|
| `RoundStart` | if the local player is in `seats`, build the whole UI and `controls:hide()`. **If not, build nothing** — a hider never gets the card overlay. Store the seat poses for plan 04-19 |
| `Sync` | `reducer:onSync(payload)` -> `hand:apply(display, changes, selected)`, `piles:setLeft/setRight`, and the countdown: show it only while `idleDeadlineUnix - Workspace:GetServerTimeNow() <= Config.Card.AFK_WARN_SECONDS` (D-16) |
| `Table` | `reducer:onTable(events, depths)` -> depths to plan 04-19's table view; a `Completed` for the **local** seat calls `controls:onLocalCompleted()`, which destroys the overlay, restores controls and **then** starts the flourish (D-30) |
| `Notice` | `reducer:onNotice(notice)` then `strip:setMessage(Hints.MESSAGES.<code>(...), Config.Card.TWEEN.NOTICE)` |
| `Stall` | `strip:setMessage(Hints.MESSAGES.stall(), Config.Card.STALL_CUE_SECONDS)` on `active`, clear on not |

**Input wiring:** `tapSlot`/`tapOff`/`tapLeftPile`/`tapRightPile` and the keyboard accelerators all
call the **reducer**, and whatever `Emit` it returns is sent through `ClientNet.send`. The renderer is
then updated from the reducer's own display. **There is exactly one path from an input to a sent
intent and it goes through the reducer** — which is what makes plan 04-09's CARD-15 assertion
describe the shipped game and not a model of it.

**A per-frame `RenderStepped` step** calls `reducer:tickWatchdog(nowDeci)` and refreshes the
countdown. `nowDeci` here is a **client-local display clock only** (rule 5): it is never sent, never
compared with a server value, and nothing a score depends on reads it. Say so in a comment.

`src/client/Main.client.luau`: `ClientNet.resolve()` **first**, then `CardClient.new():start()`,
then the existing `Ping`. Resolve before anything else, because `WaitForChild` is a yield point and a
gameplay message arriving at an unresolved remote is dropped.
