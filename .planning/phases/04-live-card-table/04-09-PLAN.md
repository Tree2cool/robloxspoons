The client's whole decision layer for CARD-02, CARD-14 and CARD-15, as a pure reducer over
`auth + pending[]` — so "feels immediate at 150-300 ms with the server correcting any mismatch
without a visible glitch" becomes a virtual-time unit test rather than a feeling.

Purpose, and the three decisions this file is the sole home of:

- **D-10:** the action is applied locally the instant it commits, before any acknowledgement.
  Waiting for the ack is a visible stall on every single pass.
- **D-02 / D-03 / CARD-15:** there is **no gate, debounce or arming delay**. The requirement rests
  entirely on *"one tap alone never sends a card"*, which is literally what success criterion 1
  asks for. **The residual is recorded and accepted:** a fumbled fast double-tap on a single card
  WILL send that card. Do not add a debounce later to "fix" it without re-opening D-02 — it was a
  deliberate trade, in the owner's own words: *"Honestly remove the 0.5s, make it instant."*
- **D-11 / D-12:** a correction and a hard rejection look **identical** — a short deliberate motion
  back into the hand, no text, no toast, no colour flash, no sound. The reject code never reaches
  the client. A message would be noise for a legitimate player and would hand a prober the name of
  the guard they tripped.

This plan also settles `04-RESEARCH.md`'s **Open Question 5** (resync mechanism); see task 1.

```luau
--!strict
local Card = require("../Config/Card")

export type FaceRecord = { cardId: number, rank: number, copy: number }

-- The last Sync. The ONLY source of truth for my own hand: a public `Drew` for my own seat carries
-- an id with no face (Pitfall 12), so the hand is never built from the public batch.
export type Auth = {
	ackSeq: number,
	seat: number,
	hand: { FaceRecord },       -- in ARRIVAL ORDER, never re-sorted by rank
	inbox: number,              -- my left pile depth, exact (CARD-13)
	downstream: number,         -- the next seat's inbox depth, exact
	idleDeadlineUnix: number?,  -- published only on arm/re-arm (D-16); display only
}

export type Pending =
	{ seq: number, kind: "Draw", sentAtDeci: number }
	| { seq: number, kind: "Pass", cardId: number, sentAtDeci: number }

-- A face-down placeholder has `cardId == nil`: the client does not know the id of the card it just
-- drew, because a Draw intent names no card. That is why an Arriving card is not tappable yet --
-- information-limited, not a timer, and it adds no delay beyond the round trip (UI-SPEC).
export type DisplayCard = { cardId: number?, rank: number?, copy: number? }
export type Display = { hand: { DisplayCard }, inbox: number, downstream: number }

-- What the renderer animates. D-12: there is NO reason, code or message field on any variant, and
-- there must never be one. A correction, an engine rejection, a shell rejection and a gateway
-- rate limit all arrive here as the same `Returned`.
export type Change =
	{ kind: "Added", cardId: number? }
	| { kind: "Flipped", cardId: number }
	| { kind: "Returned", cardId: number }   -- D-11: a short deliberate motion back into the hand
	| { kind: "Removed", cardId: number }    -- server-initiated: AFK auto-pass or ValveForcedPass

export type Emit = { name: "Draw" | "Pass", payload: { [string]: number } }

export type Reducer = {
	-- INPUT FROM THE UI. Each returns the intent to send, or nil.
	tapSlot: (self: Reducer, cardId: number?, nowDeci: number) -> Emit?,
	tapOff: (self: Reducer) -> (),
	tapLeftPile: (self: Reducer, nowDeci: number) -> Emit?,
	tapRightPile: (self: Reducer, nowDeci: number) -> (),   -- D-06 sink: keeps the selection, sends nothing
	-- INPUT FROM THE SERVER.
	onSync: (self: Reducer, auth: Auth) -> { Change },
	onTable: (self: Reducer, events: { any }, depths: { number }) -> { Change },
	onNotice: (self: Reducer, notice: any) -> { Change },
	-- TIME.
	tickWatchdog: (self: Reducer, nowDeci: number) -> { Change },
	-- OUTPUT TO THE RENDERER.
	display: (self: Reducer) -> Display,
	selectedCardId: (self: Reducer) -> number?,
	pendingCount: (self: Reducer) -> number,
	depths: (self: Reducer) -> { number },
	sinkHintUntilDeci: (self: Reducer) -> number?,
	idleDeadlineUnix: (self: Reducer) -> number?,
}

Prediction.new = function(pendingTimeoutDeci: number): Reducer
```

**`display` is `fold(pending, auth)`, computed, never stored:** a `Pass` removes its `cardId` from
the hand and adds 1 to `downstream`; a `Draw` subtracts 1 from `inbox` and appends a placeholder
`{ cardId = nil }`.

**`tapSlot`, exhaustive (D-01 through D-04, F6):**

| Situation | Effect | Returns |
|---|---|---|
| `#display.hand ~= 5` | **nothing at all.** Selection unchanged. At hand 4 the player owes a *draw*, and a Pass would be a guaranteed `HandNotFive` rejection, which D-12 says a legitimate player must never experience (checker FLAG F6) | `nil` |
| `cardId == nil` or not in the display hand | nothing | `nil` |
| `cardId ~= selected` | selection moves to `cardId` (D-04: "selection follows the tap") | `nil` |
| `cardId == selected` | **commit** (D-01): append `Pass` to `pending`, bump `nextSeq`, clear the selection, remove the card from the display fold | `{ name = "Pass", payload = { seq = n, cardId = cardId } }` |

There is **no debounce, no arming delay and no timestamp comparison** anywhere in `tapSlot`
(D-02/D-03). `nowDeci` is used only to stamp the pending entry for the watchdog.

**`tapLeftPile` (D-07):** instant and unguarded, but only legal at hand 4 with `inbox >= 1`;
otherwise returns `nil` and changes nothing. Emits `{ name = "Draw", payload = { seq = n } }`.

**`tapRightPile` (D-06):** a no-op sink. It **keeps** the selection — a fumbled tap must not
deselect a card the player is about to send — and sets `sinkHintUntilDeci = nowDeci + TWEEN.SINK_HINT * 10`
so plan 04-16 can pulse the strip hint. It never emits.

**`onSync`, exhaustive:**
1. if `auth.ackSeq < current.ackSeq`, **ignore entirely** and return `{}` (monotonicity: an
   out-of-order or stale Sync must not resurrect a resolved state);
2. replace `auth`;
3. drop every pending entry with `seq <= auth.ackSeq` — **cumulative ack**: anything at or below the
   ack that the new `auth` does not reflect was rejected;
4. re-fold and diff the old display against the new one:
   - a card absent now that was present and had been **predicted away** and whose pending entry was
     just dropped -> nothing (the server agreed);
   - a card present now that we had predicted away -> `Returned` (D-11);
   - a placeholder resolved to a real id -> `Flipped`;
   - a card newly present that we did not predict -> `Added`;
   - a card absent now that we did **not** predict away -> `Removed` (forced out);
5. if the selected card is no longer in the display hand, clear the selection **silently**.

**`onTable`:** fold `depths`; ignore own-seat `Drew` and `Passed` for the hand (the hand comes only
from `Sync`); return `{}` for the local hand and let the renderer read `depths()`.

**`onNotice`:** `ForcedPass` and `Strike` do **not** touch `pending`; they are server-initiated, so
the hand change arrives with the accompanying `Sync` as a `Removed`. `onNotice` clears the selection
if the notice names the selected card and otherwise changes no state. It returns `{}`; the cue
itself is the renderer's job.

**`tickWatchdog` — the resolution of `04-RESEARCH.md` Open Question 5.** **Decision: the watchdog
rolls back LOCALLY, and no `Resync` intent is added.**

> A gateway-level rejection (`RateLimited`, `WrongPhase`, a validation failure) never reaches the
> card core, so its `seq` is never acked individually. The **primary** fix is a server push: plan
> 04-14 wires the existing `onReject` sink so a rejected card intent also sends that player a `Sync`
> carrying the current `ackSeq`, which resolves the pending entry cumulatively. This watchdog is the
> **backstop** for the case no push can cover — a message genuinely lost, which the platform
> documents as possible on disconnect.
>
> When the oldest pending entry is older than `PENDING_TIMEOUT_SECONDS` (1.0 s), the reducer drops
> it and re-folds, emitting `Returned` for a `Pass` and `Removed` for the placeholder of a `Draw`.
> **The alternatives were a `Resync{seq}` intent and a no-op.** A new intent means a new manifest
> row, a new bucket and a new client-driven path a prober can poke, for a case where `auth` is
> already authoritative — rolling back to `auth` is always correct, because `auth` is what the server
> said. The no-op leaves a card visibly gone forever, which is precisely the "visible glitch"
> success criterion 2 forbids.
>
> **The trade-off, stated plainly:** if a `Sync` was merely slow rather than lost, the card returns
> and may then leave again when the `Sync` lands. At 150-300 ms a 1.0 s timeout means roughly three
> round trips have passed, so this is rare, and a brief double motion is a far smaller defect than a
> card that never comes back. The timeout is a UI timing value in `Config.Card`, not a scoring
> value.

A rolled-back entry must be marked so the watchdog does not re-fire on it every tick.
