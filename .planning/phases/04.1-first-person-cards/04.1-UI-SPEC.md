## Card Geometry in World Space

The hand is built in **camera-local space** and converted to world space once (`handCF = cameraCF * CFrame.new(HAND_OFFSET)`). Roblox looks down -Z, so the offset is:

| Constant | Value | Reason |
|---|---|---|
| `HAND_OFFSET` | `Vector3.new(0, -2.2, -6.5)` studs (right, up, forward = 6.5) | Distance 6.5 and drop 2.2 are the two numbers that set size and screen position; both chosen from the prototype sweep (Proof section) |
| `STUDS_PER_DESIGN_UNIT` | `1/40` | 72 x 92 design card = **1.8 x 2.3 studs**; the ratio is exactly 72:92. Every Phase 4 token converts by /40 |
| `CARD_STUDS` | width 1.8, height 2.3, thickness 0.05 | |
| `STEP_STUDS` | 1.5 (= 60 units) | chord between neighbouring card centres |
| `ROLL_STEP_DEG` | 4 | per-slot roll about the view axis; slot s of n gets `(s - (n+1)/2) * 4` degrees, so a 5-card hand spans -8..+8 and a 4-card hand -6..+6 |
| Arc radius | derived: `R = STEP_STUDS / (2 * sin(ROLL_STEP_DEG/2))` = 21.5 studs | one constant fewer: radius is derived, never stored (the Phase 4 "derived values are derived" rule) |
| `LEAN_DEG` | 12 | each card's top leans *away* from the camera (top farther by `h * sin 12`). Foreshortens height by cos 12 = 0.978 |
| `LIFT_STUDS` | 0.4 (= 16 units), along the card's own up vector | |
| Slot centre | pivot at `(0, -2.2 - R, -6.5)`; slot centre = pivot + `R*(sin rho, cos rho)`, card rolled by `-rho`, `rho = roll` | the ends dip `R(1 - cos 8 deg)` = 0.21 studs = 8.4 units below the middle: a held-hand curve, not a flat row |
| Layering | slot s gets `ZOffset = s` and a camera-ward depth step of 0.05 studs; right neighbours sit on top | matches Phase 4 ("later cards sit above earlier ones") |
| Hand-size 4 | the same constants with n = 4; the fan re-centres (centre of hand stays at the offset) | tween `CLOSE_GAP` 0.12 s, hit rects snap at once (Phase 4 F7, accepted) |

**Rendering carrier (Decided #1).** One anonymous `Part` per live card in `workspace.CurrentCamera` (client-local container), `Anchored`, `CanCollide=false`, `CanQuery=false`, `CanTouch=false`, `CastShadow=false`, `Transparency=1`, size = `CARD_STUDS`, **Name = `"CardSlot"` for every card and no Attributes**. The face lives in a `SurfaceGui` parented to **`PlayerGui`** with `Adornee = part`, `Face = Front`, `SizingMode = PixelsPerStud`, `PixelsPerStud = 40 * CANVAS_SCALE` (`CANVAS_SCALE = 3`), `AlwaysOnTop = true`, `Active = false`, `ZOffset = slot`. Inside it: one `UIScale` of `CANVAS_SCALE` and the unchanged 72 x 92 `CardFace` tree. `CANVAS_SCALE = 3` keeps texel density >= 1 per screen pixel up to `k = 3`, i.e. up to H = 1092 (so 1080p is exactly covered; 1440p and 4K are slightly soft - accepted, see Open Questions).

- VERIFIED (SurfaceGui.md, 2026-11-10T00:40:48Z): `AlwaysOnTop = true` "always renders on top of 3D content", "colors match how they appear inside a ScreenGui", "text may appear sharper on high DPI devices", `LightInfluence` treated as 0, `Brightness` no effect. **Consequence that matters:** the face renders with authored colours, not scene lighting, so the machine-gated 4.5:1 luma floor and D-24 greyscale rule measure what the player sees. It also means the hand cannot be clipped by table geometry or the avatar.
- VERIFIED: `SizingMode`/`CanvasSize`/`PixelsPerStud` semantics (SurfaceGui.md). A large pixel density "could negatively affect performance" - D-54 measures it.
- VERIFIED: a SurfaceGui is only input-receptive when in `PlayerGui` and the adornee has `CanQuery`; we set `Active=false` and `CanQuery=false` **on purpose**: cards never take input, hit testing is the 2D buttons (D-47, and Phase 4's "the card is never active").
- UNVERIFIED: how two `AlwaysOnTop` SurfaceGuis on *different* parts order against each other. SurfaceGui.md says `ZOffset` "layers this SurfaceGui in relation to others on the same face", which is a different statement. Verification debt U3; M-check required; fallback in Open Questions.

## Projection and the 48 px Proof (D-43, D-47, D-52)

### The function
A pure module `src/shared/Card/Projection.luau` (**no Roblox types**, like `Layout`) maps a viewport to every card's screen geometry. It does *not* call `Camera:WorldToViewportPoint`; it implements the pinhole model directly so it runs headless:

```
tanHalf = tan(FOV/2)                      -- FOV = 70
pxPerStudAtDepth(z) = fullH / (2 * z * tanHalf)
screen(x, y, z)  = ( fullW/2 + (x/z)/tanHalf * fullH/2 ,  fullH/2 - (y/z)/tanHalf * fullH/2 )   -- camera space, z = depth forward
k(fullH) = fullH / (2 * 6.5 * tanHalf * 40) = 0.0027466 * fullH      -- screen px per design unit at the hand centre
```
`fullW x fullH` is the **fullscreen area**, not `Camera.ViewportSize`: VERIFIED that `FieldOfView` "is based on the fullscreen area, not ViewportSize", the camera "renders in the fullscreen area", and `ViewportSize` is the device safe area "in Roblox UI offset units which may be different from native display pixels" (Camera.md). Fullscreen size comes from the `AbsoluteSize` of an inset-`None` probe `ScreenGui` (VERIFIED as the documented method, Camera.md `ViewportSize` entry). **Because the card's projected rect depends on `fullH` and the fixed FOV only, it is a pure function of the viewport. That is D-43's whole claim.**

Tying the model to the engine: a Studio conformance check (M-check A) projects the 8 corners of every card with the real `Camera:WorldToViewportPoint` and asserts each is within **1 px** of `Projection`, at three viewport sizes. The origin of `WorldToViewportPoint` (fullscreen vs device-safe area) is not stated by the docs (VERIFIED text: "offset from the top left corner of the viewport, in pixels", ignores GUI inset; `WorldToScreenPoint` "takes in account the current GUI inset"). That ambiguity is exactly what check A resolves, and why production code does not call either.

Fullscreen coordinates are converted to the `CoreUISafeInsets` `ScreenGui`'s own coordinates by subtracting `(insets.left, insets.top)`, the same convention `Layout.safeRect` already uses. VERIFIED: under `CoreUISafeInsets` `AbsolutePosition`'s origin is the bottom-left of the Roblox top bar (GuiBase2d.md). **UNVERIFIED (U5):** that this origin equals `(insets.left, insets.top)` in fullscreen coordinates on a notched device. Phase 4 already assumed it; check A also asserts it with a probe.

### Governed quantity: projected card HEIGHT (vertical), width follows
`FieldOfView` is the VERTICAL angle (VERIFIED), so the quantity this contract governs is the **projected card height as a fraction of fullscreen height**: `cardH_px = 92 * k(fullH) * cos(LEAN) = 0.2471 * fullH` at rest (PROTOTYPE), constant across every aspect ratio. Projected width follows as `0.7826 * height` and the fan's horizontal extent follows as a multiple of `fullH`, not `fullW`; that is why a narrow aspect (4:3) is the binding case for the *fan-to-pile gap* (horizontal) while the narrow *height* (360) is binding for the 48 px floor. Both are asserted separately (tests 1 and 5). **Use `Camera.FieldOfView`, never `Camera.DiagonalFieldOfView`**: the diagonal property is documented as the FOV of the fullscreen area "which may be occluded by notches or screen cutouts" and changes with aspect, which would make card height viewport-dependent in a way the 48 px proof does not model. A later reader must not swap them; `projection.spec` fixes `FOV_DEGREES` as the vertical angle by name, and the lock sets `FieldOfViewMode = Vertical` so the engine keeps it that way on resize.

### Inset coordinate pin (decision: option (b), explicit)
`WorldToViewportPoint` **does not account for the GUI inset** (VERIFIED, Camera.md 2026-11-10T00:40:47Z: "the 2D position returned is taken from the top left corner of the viewport. Unless you are using ScreenGui.IgnoreGuiInset, this position is not appropriate for placing GUI elements"). The hit layer **keeps `CoreUISafeInsets`** (V-24; UX-03 requires nothing interactive under a notch or the top bar), so **option (a) is rejected**: it would make UX-03 rest on card geometry staying clear of the unsafe area, and the cards' lowest edge (0.930 H) already leaves only 6 px of slack on the notched reference.
- **Rule:** no production code converts a projected point with `WorldToViewportPoint`/`WorldToScreenPoint`. `Projection` yields **fullscreen-origin** pixels; the hit layer subtracts one `origin = (insets.left, insets.top)` from every rect before assigning `Position`. `origin` is measured at runtime, not assumed, **with one documented call**:

```lua
local area = game:GetService("GuiService"):GetInsetArea(Enum.ScreenInsets.None)
local origin = Vector2.new(-area.Min.X, -area.Min.Y)   -- core-UI origin -> fullscreen origin
local fullW, fullH = area.Max.X - area.Min.X, area.Max.Y - area.Min.Y
```

**REVISED 2026-11-10 after the UI check (F1).** The first draft derived `origin` by hand:
`left+right = fullW - cardGui.AbsoluteSize.X` plus `GuiService:GetGuiInset().Y`. That was
**under-determined and probably wrong** — a single width difference cannot separate the left inset
from the right one, and `GetGuiInset` is documented as applying to `IgnoreGuiInset = false`
ScreenGuis, which is the legacy top-bar semantic and **not** notch-aware `CoreUISafeInsets`. The
headless `projection_inset.spec` takes insets as given, so it could never have caught the error;
only a notched device would have, and it would have shifted every hit target by the top bar.

**VERIFIED (GuiService.md, 2026-11-10):** `GetInsetArea(screenInsets: ScreenInsets): Rect` "returns
a `Rect` describing the inset region **relative to the `CoreUISafeInsets` area**". The documented
example, `-59, -58, 792, 334`, means the usable rectangle for `ScreenInsets.None` begins 59 px left
and 58 px up from the core-UI origin. So `-Min` IS the origin and `Max - Min` IS the fullscreen
extent — both, correctly, from one call, with no probe `ScreenGui`. This also moves **U5 to
VERIFIED**.

The cross-check against `Layout.safeRect` is kept but **demoted to a diagnostic**, because the UI
check observed it may be circular: a mismatch over 1 px logs by name rather than deciding
correctness. **M-check A remains the only thing that proves the rects land on the cards.**
- **Consequence for UX-03:** the 2D chrome (strip, piles, callouts, rail) sits inside the safe rect as in Phase 4, and the hit rects are *by arithmetic* inside the cards, which are asserted inside the safe rect (test 3). A hit rect can never be under the notch because the card is not.
- **Acceptance test (headless, `projection_inset.spec`):** for the reference notched viewport (844x390, insets L 47, R 47, T 0, B 21, then again with T 24 to model a top bar), assert for every slot that `hitRect + origin` (back in fullscreen coordinates) lies inside the fullscreen-projected exposed polygon of that card to within 1 px, and that the hit rect centre, projected back into fullscreen, hits the card's own projected quad. **Mutation:** drop the `origin` subtraction (or subtract only `top`) and the spec must fail at insets > 0; with all insets 0 it must still pass, proving the test is not vacuous and that a desktop-only run could not have caught the bug.
- **Acceptance test (device, M-check A, mandatory on a notched phone):** with a debug overlay that draws the pure card quads as 2 px outlines in the same `ScreenGui` and the hit buttons at 30% opacity, the outline, the 3D card and the button must coincide within 2 px at all five slots. Non-zero inset required; a zero-inset device does not satisfy this check.

## Hit Model (D-47) and Occlusion Ordering

**Visual is 3D, input is 2D.** One invisible `TextButton` (`Text=""`, `BackgroundTransparency=1`, `AutoButtonColor=false`, `Active=true`) per slot, in the existing `CoreUISafeInsets` card `ScreenGui`, positioned on the projected rect. Cards and their `SurfaceGui`s are never `Active`.

**Rect derivation (per slot i, per hand size, per viewport; recomputed on `ViewportSize` change; never per frame):**
1. Project the 4 corners of card i at rest and at lifted pose (`Projection`).
2. Exposed polygon = card i's projected quad minus everything to the right of card i+1's projected **left edge line** (top-left to bottom-left, rest pose). The last card is not clipped.
3. Vertical span = `[max(liftedTL.y, liftedTR.y), min(restBL.y, restBR.y)]` (the lifted top to the resting bottom: Phase 4's "card + lift" height, with the slanted edges excluded so every point inside the rect is on a real card).
4. Horizontal span = intersection, over that vertical span, of the exposed polygons at rest and lifted.
5. Snap inward to integer px (left/top `ceil`, right/bottom `floor`) and subtract `(insets.left, insets.top)`.
This rect is an **inscribed** rectangle, not a bounding box. Consequences: (a) every tappable point is on a card, so a tap on the table between cards is a backdrop tap, not a card select (Phase 4 D-04 intact); (b) the 48 px assertion measures real tappable area; (c) neighbouring rects are **disjoint by construction**.

**Ordering.** Because rects are disjoint, ordering is a belt-and-braces rule rather than the mechanism: button `ZIndex = 10 + slot` so the right-most (visually top) card wins any 1 px rounding overlap, and a test asserts pairwise `separation >= 0` (as Phase 4's hit-overlap check) so the ZIndex rule is never load-bearing.

**Selected card.** Its rect is unchanged by the lift (it already spans rest-to-lifted by step 3), so the second tap lands where the first did (D-01). **Known behaviour, accepted, carried from Phase 4:** the lifted card's visible overhang on its right neighbour belongs to the neighbour's rect; tapping it selects the neighbour. Widening the lifted rect would shrink the neighbour's width below the floor.

**Inert at hand 4, sinks, backdrop, keyboard/gamepad accelerators (1..5, Space, A):** unchanged from 04-UI-SPEC. The backdrop stays a full-screen `Active` button beneath everything.

**Hit rects jump to final layout at the instant of a commit**; visuals tween (Phase 4 F7, unchanged). Rects are computed from the *final* pose, never from a tween's current CFrame.

**Raycast hit testing is rejected** (D-47 reason repeated so a later reader does not reopen it): it would make the target size depend on the physics query rather than on the viewport.

## Face Legibility at the New Size (D-48, D-53, CARD-19, D-24)

- Vocabulary is untouched: `Faces`, 50 identity keys, `(rankGlyph, pipShape)`, greyscale rule, 4.5:1 luma gate (`renderer_discipline.spec`), `CardTheme` as the single colour/font home. Passing: **no new colour, font or stroke is introduced by this phase.**
- **Minimum rendered pip = 14 px.** Derivation: Phase 4's smallest rendered pip was 16 x 0.85 = 13.6 px; 14 is that floor rounded to a whole pixel and may never be lower. Assertion (headless): `16 * k(fullH) * cos(LEAN_DEG) >= 14` for every supported viewport with `fullH >= 360`; at 640x360 it is **15.5** (margin 1.5 px). Rank glyph likewise `20 * k * cos(12 deg) >= 17` (Phase 4 minimum 17.0) - measured 19.4 at 640x360. A card's `lean` and `roll` only ever reduce size by `cos`, so both are included in the formula.
- **The pip cannot silently shrink in the canvas:** the `UIScale` is exactly `CANVAS_SCALE` and `renderer_discipline` gains a rule that no `UIScale`, `TextScaled`, or size literal other than the `CardTheme.TEXT_SIZE`/`Layout` design units appears in the face path.
- **The 3 px selection outline** stays a face stroke (selection = lift **and** stroke thickness, D-24), so it is carried by the card surface and is also thicker on jokers as before.
- **M-14 is re-run** (D-53): spade vs club first, on desk **and** on glass, at the rendered size above. The desk half signed 2026-11-09 judged flat 72 x 92 faces and **does not transfer**. The test grid renders all 50 corner indices through the *real 3D path* at 640x360 and 844x390 (the two sizes where the pip is smallest), **with greyscale COMPUTED in the probe — Rec. 709 luma applied to every colour — and not `ColorCorrectionEffect`.**

**Never gates input (D-50).** No input handler reads a tween's state, `Completed` event or an "animating" flag; the reducer owns the hand and the tween is decoration. ## Privacy (D-45, D-46) - the highest-risk part of the phase

**Design.** (1) All rank/copy information exists only as `GuiObject`s under `PlayerGui` (client-local by construction, the same mechanism that made the Phase 4 overlay private). (2) The Parts that carry the SurfaceGuis are **anonymous**: identical size, `Name = "CardSlot"`, no Attributes, no rank-bearing child, `Transparency = 1`, parented under `workspace.CurrentCamera`. So even if a Part *did* replicate (U1), it would reveal "someone has a card here", which is what a count already tells everyone, and no rank. Hand size of *other* seats is public (CARD-13); *this* client's hand size is the only thing a replicated carrier could add, and it is derivable from public pile counts. (3) Other seats get no card objects at all (D-46).

**Acceptance tests.**
- **T1, source scan (headless, `privacy_3d.spec`).** In `src/client`, every `Instance.new("Part")`/`:Clone()` that produces a card carrier is parented into `Workspace.CurrentCamera`; no `Parent = workspace` / `Workspace` / `ReplicatedStorage` assignment exists in the card UI modules; no `SetAttribute`, `Name = <variable>` or `Name = ...rank...` appears on a carrier. Mutation: change one carrier parent to `workspace` and the scan must fire. States its own weakness (does not run the engine).
- **T2, structural (headless).** The module that builds a carrier takes no `rank` or `cardId` parameter (signature check); `cardId` is used only as a Lua table key, never written to an Instance.
- **T3, runtime probe, authoritative (M-check C, Studio 2-player server).** A *server* script, at 1 Hz during a round, walks `Workspace`, `ReplicatedStorage` **and every `Players/*/PlayerGui`** descendant and asserts: zero instances named `CardSlot`; zero instances carrying any attribute or `StringValue`/`IntValue` whose value is a rank glyph or a 1..12 rank; zero `SurfaceGui`/`TextLabel` descendants anywhere on the server's tree that contain a rank glyph (`Faces.RANK_LADDER` entries or pip codepoints). The same scan from a *second client* (the cheat client's view) over its own `Workspace` **and over `Players/<other>/PlayerGui`** must also find none.

**REVISED 2026-11-10 after the UI check (F3).** The first draft scanned only `Workspace` and
`ReplicatedStorage`. **U2 is a claim about client-created `PlayerGui` descendants, and that scan
never visited `PlayerGui` at all** — so the test could not falsify the very thing it existed for,
and the second-client scan of its own `Workspace` was close to vacuous for U1. D-45 is the largest
new risk in this phase; its gate must be able to fail.

**Non-vacuity is mandatory here, not optional:** the probe must first be run against a deliberately
planted carrier — a Part named `CardSlot` with a rank attribute, parented to `workspace` — and
must fire. A privacy gate that has never been seen to fail is not evidence. This is the only test
that can falsify U1/U2 for real; T1/T2 only guard the code.
- **T4, `privacy.spec` is not edited.** It keeps proving the network half (per-player send of the face record). 04.1 adds nothing to the network, so the spec passing unchanged is itself an acceptance criterion.
- **T5, other seats:** `CardSeatsView` creates no instance whose count of children encodes anything but `min(count, SEAT_STACK_CAP)` (existing); the depth rail's bars are a pure function of public counts, asserted by feeding two states with equal public counts and different private hands and comparing the rendered tree (must be identical).

## Decided without the owner

Each was a fork CONTEXT.md left open. I took the most conservative branch (the one that preserves an existing guarantee or adds the least).

1. **Card carrier is a blank client-local Part + a `PlayerGui` SurfaceGui, with `AlwaysOnTop = true`.** Why: the face data never leaves `PlayerGui`, which is the Phase 4 privacy mechanism, so D-45 does not newly depend on a platform claim I could not verify. AlwaysOnTop gives authored colours (keeps the luma gate honest) and removes clipping against the table and avatar. Rejected: `ViewportFrame` (no cost evidence, normalised-coordinate quirk), server-side parts (violates rule 3), `BillboardGui`s (no lean/roll geometry).
2. **No `ViewportFrame` anywhere.** Same reason; also it keeps "no per-frame work".
3. **Pile panels stay 2D, not 3D stacks.** Why: it carries forward the 84 x 96 hit rects, their layout tests and `CardPiles` unchanged; a tappable 3D pile would need its own projected-rect proof. Cost: less "at the table". Upgrade path exists: the flight anchors are already world points.
4. **Added a non-interactive depth rail** for other seats. Why: success criterion 4 (CARD-13) cannot be met by 3D stacks outside a 70 degree-vertical fixed frustum. It shows only public counts, no numerals. This is the one place I *added* UI, so it is Open Question 1.
5. **One travel duration `CARD_MOVE = 0.18`** for draw, pass, return and deal (D-51 read literally). 0.18 is the existing SEND value, the longest of DRAW/SEND without making return feel slow; 0.25 return is dropped.
6. **FOV 70 (the engine default).** D-43 required it be fixed; 70 means a restore to default is a no-op for most players and the Phase 4 horizon maths is familiar. Not a tuned art choice.
7. **The hand is placed in camera-local space once**, with the camera at `seat.position + 2.5 up`, not on the avatar's head (D-42).
8. **Table band bound lowered 58% -> 47% and measured to the strip top**, and the TableRegion projection test replaced by a seat-visibility report (see disposition table).
9. **Character parts set to `LocalTransparencyModifier = 1` while locked.** Why: otherwise the head/accessories sit at the near plane. Client-only, restored the same frame as the camera.
10. **Pure `Projection` module instead of calling `WorldToViewportPoint`.** Why: the docs leave the call's origin ambiguous (fullscreen vs device-safe area), and a pure model is the only way the 48 px floor can be a headless assertion, as `Layout` is.
11. **Supported aspect range 4:3 .. 21:9, smallest 640x360.** 4:3 is included because an iPad in landscape is a real Roblox device and it is the binding case for fan-to-pile gap (+12 px); narrower than 4:3 is unsupported and the plan must make the lock report it rather than degrade silently.
12. **Pulses (AFK/stall) move to the card face stroke** rather than inventing a floating outline in 3D.

### Open Question 2, expanded — the layering spike (REVISED 2026-11-10 after the UI check, F2)

**A fan whose layering is wrong is not a fan.** Later cards must sit above earlier ones or the
overlap reads as noise and the corner index — the only part of a covered card a player can see —
is drawn by the wrong neighbour. This phase cannot be planned around an unresolved answer here,
because the answer decides what a card *is*.

**Why the first draft's fallback was withdrawn.** It said: one Part, one SurfaceGui for the whole
hand, cards as frames inside it, roll and lean as 2D `Rotation` plus a vertical squash. That is not
executable:
1. It never says how lean and roll become 2D transforms, and a squash is not a perspective foreshortening.
2. **A single plane cannot give each card its own perspective quad.** The pure `Projection` module
   emits pinhole quads per card; under one shared plane those quads would no longer describe
   anything on screen.
3. So **the 48 px proof and every hit rect would be derived from geometry that is not being drawn** —
   the precise failure D-47 exists to prevent, reintroduced by the fallback meant to save it.
