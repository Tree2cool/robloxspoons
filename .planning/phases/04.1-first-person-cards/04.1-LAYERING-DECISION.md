# Phase 04.1 — the layering decision (Wave 0 spike)

**Status: the question is written down, the probe is committed, the provisional route ships, and the
observation is MANUAL-CHECKS M-18, which is unsigned.** Written by plan 04.1-01 on 2026-11-10.

## The question, in one paragraph

Each card in the first-person hand is an anonymous `Part` carrying a `SurfaceGui` whose face is the
unchanged Phase 4 `CardFace` tree. Five cards overlap: card *s+1* must draw **over** card *s*, or
the overlap reads as noise and the corner index — the only part of a covered card a player can see —
is drawn by the wrong neighbour. The spec achieves that with `AlwaysOnTop = true` plus
`ZOffset = slot` plus a 0.05-stud camera-ward depth step. **No primary Roblox doc says that works.**
Re-verified against `SurfaceGui.md` on 2026-11-10: `AlwaysOnTop = true` means the GUI "always renders
on top of 3D content", and `ZOffset` "layers this SurfaceGui in relation to others **on the same
face**" and "does not visually 'lift' or 'sink' a SurfaceGui from the surface". **Neither sentence
covers two `AlwaysOnTop` SurfaceGuis on different Parts.** If `AlwaysOnTop` bypasses depth testing
then the 0.05-stud step is meaningless and `ZOffset = slot` is the wrong mechanism; if it does not,
the step is the mechanism and `ZOffset` is noise. The two possibilities disagree about **what a card
physically is**, which is why this gates the phase rather than sitting in a backlog. Verification
debt ID: **U3**.

## The three routes

Each row gives the property assignments that implement it, what it costs if chosen, and what else in
the phase changes.

### Route A — `AlwaysOnTop = true`, `ZOffset = slot` (the spec as written)

| | |
|---|---|
| **Assignments** | `SurfaceGui.AlwaysOnTop = true`, `SurfaceGui.ZOffset = slot`, `LightInfluence = 0`, and the 0.05-stud depth step is present but not load-bearing |
| **Cost if chosen** | **Nothing.** This is the spec as written and nothing in the phase changes |
| **What else changes** | Nothing. M-23 stays NOT APPLICABLE |
| **Why it is the provisional route** | see below |

### Route B — `AlwaysOnTop = false`, real depth testing via the 0.05-stud step

| | |
|---|---|
| **Assignments** | `SurfaceGui.AlwaysOnTop = false`, **no** `ZOffset`, `LightInfluence = 0`, and the 0.05-stud camera-ward step per slot is now **the** layering mechanism |
| **Cost if chosen** | **(i)** the hand can be clipped by table geometry and by the avatar, because ordinary depth testing is back. **(ii)** Scene lighting is back in principle, which would modulate the face colours and so put the machine-gated 4.5:1 luma floor in doubt — the floor is honest *because* the authored colours are what render. The mitigation is `LightInfluence = 0` (below), which shrinks (ii) from a re-measurement to a confirmation |
| **What else changes** | `Card.HAND.LAYERING_ROUTE = "Depth"`; two assignments at the carrier's one creation site; **M-23 goes live and blocking**; M-18 must also record whether occlusion was observed |
| **Determinism** | **Deterministic by construction.** This is the route's real attraction: depth testing is a documented, ordinary mechanism, not an undocumented interaction between two `AlwaysOnTop` surfaces |

### Route C — one `SurfaceGui`, per-card quads drawn by `Projection` into 2D

| | |
|---|---|
| **Assignments** | one Part, one `SurfaceGui`, five `Frame`s, `ZIndex = slot`; the card corners come from the pure `Projection` module rather than from world-space geometry |
| **Attraction** | deterministic, and it keeps `Projection` authoritative — the quads drawn would **be** the quads proven |
| **Cost if chosen** | **ROUTE C IS A BLOCKER-GRADE REWRITE, NOT A FALLBACK.** See the finding below |

#### The finding that makes route C the expensive last resort

**Vanilla Roblox `GuiObject`s have no shear and no skew.** A `Frame` can be positioned, sized and
rotated; it cannot be sheared. Lean (12 degrees) and roll (up to 8 degrees) together produce a
**perspective quad** — four corners with no two opposite edges parallel — and a perspective quad is
**not** a rotated rectangle. So route C cannot be implemented by placing or rotating `Frame`s. It
leaves exactly two sub-options, and both are expensive:

1. **Accept parallelogram approximations.** Then the drawn corners are **not** the proven corners,
   and the 48 px proof and every hit rect are derived from geometry that is not on screen — **the
   precise failure D-47 exists to prevent**, reintroduced by the thing meant to save it. This is also
   why the first draft's "one Part, one SurfaceGui, roll and lean as 2D rotation plus a vertical
   squash" fallback was withdrawn by the UI check (F2): a squash is not a foreshortening.
2. **New image assets**, drawn as pre-sheared textures or a mesh. That is art, an upload, a
   moderation delay and a new asset pipeline.

**Therefore route C is a BLOCKER to raise with the owner, not a route an executor may take
overnight.** M-18's Expected says so, and so does this document, in both places a reader would look.

## The decision rule, in one sentence an operator can apply from a photograph

> **With five overlapping cards whose only difference is slot index, does the right-hand card's edge
> cover the left-hand card's, at every adjacent pair, from the seated camera?**

- **Yes under route A** → **ship A.** Nothing changes.
- **No under A, yes under B, and nothing occluded under B** → **ship B.** Set
  `Card.HAND.LAYERING_ROUTE = "Depth"` and make M-23 live.
- **No under A, yes under B, but a card IS occluded under B** → **STOP, BLOCKER.** See the occlusion
  branch below.
- **No under either** → **STOP and raise route C with the owner.**

**All four adjacent pairs must be checked, including 4/5.** Three centred cards can pass while the
rolled end pair fails: slot roll is `(s - (n+1)/2) * 4` degrees, so in a five-card hand slots 1 and 5
sit at -8 and +8 degrees and the ends dip `R(1 - cos 8°) = 0.21` studs below the middle. **That is
why the committed probe builds five cards per route and not three** (threat T-4.1-05).

## The occlusion branch, which the rule needs and the first draft did not have

Route B restores depth testing, so the hand can be clipped by table geometry and by the avatar. **The
probe therefore places one opaque slab between the camera and the fan in the route-B group**, so the
cost is visible in the same photograph instead of being discovered after the route is chosen.

**If B is chosen AND occlusion is observed, that is a BLOCKER, not a flip.** The remedy is to move
`HAND.OFFSET_STUDS` — bring the hand nearer, or raise it — and `OFFSET_STUDS` is an **input to
`Projection`**. Moving it therefore re-opens:

- the **48 px hit-target proof** (the projected card height is a function of FOV, viewport height and
  the hand's distance),
- the **fan-to-pile gap** (the 4:3 binding case),
- the **containment margin** (the hand must stay inside the safe rect at every supported viewport).

Every one of those must be re-run and **re-read**, and M-19 with them. This branch is stated here
because the "a wrong answer costs one constant" claim below **is only true while route B does not
occlude**, and a reader who met the claim without the caveat would under-estimate the risk.

## `LightInfluence = 0` is set under BOTH routes, and it is why M-23 is small rather than large

**VERIFIED (`SurfaceGui.md`, re-fetched 2026-11-10):** `LightInfluence` "controls how much the
SurfaceGui is influenced by environmental lighting, in a range from 0 to 1. Setting this to 1 means
that surrounding lighting has complete control over the appearance, while setting it to 0 means that
the lighting has no effect." Separately, with `AlwaysOnTop = true`, "`LightInfluence` is treated as
though it's 0" and "Colors match how they appear inside a `ScreenGui`".

So:

- **Under route A** the property is already treated as 0. Setting it explicitly changes nothing and
  **removes a difference between the two routes**, which is what keeps the route a one-constant flip.
- **Under route B it is the whole mitigation** for the luma concern: the faces keep their authored
  colours and the machine-gated 4.5:1 floor keeps describing what the player sees.

**One addition found while re-verifying, not in the UI-SPEC: `Brightness`.** The same page documents
`Brightness` as "the factor by which the SurfaceGui container's light is scaled **when
`LightInfluence` is 0**", default 1, and states it "has no effect when either `LightInfluence` is 1
or `AlwaysOnTop` is `true`". **So under route B, `LightInfluence = 0` is necessary but not
sufficient: `Brightness` must also stay at its default 1**, or the apparent brightness of the faces
is scaled after all. Under route A it cannot matter. The carrier therefore leaves `Brightness`
untouched under both routes, and **M-23 step 2 asks the operator to confirm it reads 1**.

Because of this, M-23 shrinks from "re-measure both pips' contrast on captured pixels under two
lighting extremes" to "**photograph the same hand under the map's brightest and darkest lighting and
confirm the faces are identical**" — a confirmation that a documented behaviour holds on the shipping
engine build. The contrast re-measurement is kept as the **fallback if the photographs differ**.
Omitting `LightInfluence = 0` would have been a self-inflicted cost: it would have made route B's
acceptance a measurement rather than a check.

## The provisional route: `AlwaysOnTop`

`Card.HAND.LAYERING_ROUTE = "AlwaysOnTop"`. Four reasons, in order of weight:

1. **It is the spec as written**, so shipping it costs no edit and no re-derivation if M-18 confirms
   it.
2. **It keeps the luma gate honest without relying on anything**: authored colours, no lighting
   modulation, verified on the primary page.
3. **It cannot be clipped** by the table or the avatar, which is route B's cost (i) and the one cost
   that could cascade into the 48 px proof.
4. **The cost of being wrong is bounded** — see the next two sections.

**It is PROVISIONAL. M-18 is unsigned.** Nothing in this repository claims to know what the layering
actually does; the automated suite gates only the contract *around* the route.

## Why proceeding on a provisional answer is safe here — a property, not a hope

**Routes A and B share every geometric number.** Identical under both: the card CFrames, the slot
pivot and arc, the projected quads, the hit rects, the 48 px proof, the hit-rect disjointness, the
fan-to-pile gap, `PIP_MIN_PX` and `GLYPH_MIN_PX`. The entire difference is **three property
assignments at one creation site**:

| Property | Route A | Route B |
|---|---|---|
| `SurfaceGui.AlwaysOnTop` | `true` | `false` |
| `SurfaceGui.ZOffset` | `slot` | not set |
| the 0.05-stud depth step | present, not load-bearing | **the** layering mechanism (no code change: the step is already applied) |
| `SurfaceGui.LightInfluence` | `0` | `0` — **same under both** |
| `SurfaceGui.Brightness` | default 1 (no effect) | default 1 (**must stay 1**, see above) |

Two machine gates hold that property in place rather than leaving it as a claim in a document:

- **`tests/card/layering_contract.spec.luau`** asserts the route is one of the two legal values, that
  it has **at most one read site** in `src/` (plan 06 ratchets it to exactly 1), and that **no file
  under `src/shared/Card/` reads the route, `AlwaysOnTop` or `ZOffset`** — the geometry never knows
  which route is live.
- **Plan 02's `projection.spec`** derives every number above from `HAND`/`CAMERA` alone, so a route
  flip cannot move a projected corner.

**If B is chosen and occlusion IS observed:** the cost is a changed `OFFSET_STUDS`, which is a
`Projection` input, and the 48 px proof, the fan-to-pile gap and the containment margin must all be

**If neither route layers correctly:** route C, which is the BLOCKER-grade rewrite described above.

## The probe

`scripts/dev/spike-layering.luau`, a Studio command-bar script. It builds **five** overlapping cards
per route, side by side, at the real geometry read out of `Card.HAND` and `Card.CAMERA` (it hard-codes
no number, so the photograph is of the shipped geometry), under a camera at the real `CAMERA` pose,
with a large slot numeral on each card so a photograph is self-labelling. It prints the decision rule
and the route the config currently names, places the route-B occluder, draws route C's unsheared
approximation so the operator can see the error, and names the objects to delete afterwards. Every
part comes from one helper that sets `Anchored`, `CanCollide = false`, `CanQuery = false`,
`CanTouch = false`, `CastShadow = false`, `Transparency = 1` and `Name = "CardSlot"` — the probe
demonstrates the shipped anonymity rather than a convenient shortcut, because a probe that teaches the
pattern it is meant to forbid is worse than no probe (threat T-4.1-06).
