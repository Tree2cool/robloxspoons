## The four that must be fixed before planning

### F1 — the inset recipe is under-determined, and the fix is a documented call (HIGH)

The spec measures the inset origin by hand: `left+right = fullW - AbsoluteSize.X`, which **cannot
separate left from right**, plus `GuiService:GetGuiInset()`, which is documented as applying to
`IgnoreGuiInset = false` ScreenGuis — the legacy top-bar semantic, not notch-aware
`CoreUISafeInsets`. The headless `projection_inset.spec` takes insets as given, so it cannot catch a
wrong runtime measurement, and the 1 px cross-check against `Layout.safeRect` may be circular. Only
a device check would have caught it.

**ORCHESTRATOR VERIFIED:** `GuiService:GetInsetArea(screenInsets: ScreenInsets): Rect` exists and
does exactly this. Per the page, it "returns a `Rect` describing the inset region **relative to the
`CoreUISafeInsets` area**", with the documented example `-59, -58, 792, 334` meaning the usable
rectangle for `ScreenInsets.None` starts 59 px left and 58 px up from the core-UI origin. **One
call gives both the origin and the fullscreen extent**, notch-aware, no probe `ScreenGui`.
This also moves U5 toward verified.

### F3 — the privacy test cannot falsify its own claim (HIGH)

T3 scans `Workspace` and `ReplicatedStorage`. **U2 is about client-created `PlayerGui`
descendants**, which that scan never visits, and the second-client scan of its own `Workspace` is
close to vacuous for U1. D-45 is the phase's largest risk and its gate must be able to fail.
Add `Players/*/PlayerGui` to the authoritative server scan.

### F15 — the greyscale re-run of M-14 would be vacuous (HIGH)

The spec drives the greyscale check with `ColorCorrectionEffect.Saturation = -1`. **This phase's own
DEBT-RECHECK records that `ViewportFrame` renders no post-processing and that the effect cannot be
relied on for card UI**, and whether it touches an `AlwaysOnTop` SurfaceGui is unknown. Phase 4's
M-14 probe already computes luma itself for exactly this reason. Compute luma in the probe, and add
a coloured control swatch that must read grey — so a probe that silently fails to desaturate is
caught by the probe.

### F2 — the layering fallback is not executable (HIGH)

`AlwaysOnTop` is documented only as rendering on top of 3D content; `ZOffset` layers "in relation to
others on the same face". **Neither covers two AlwaysOnTop SurfaceGuis on different Parts**, and
AlwaysOnTop plausibly bypasses depth testing, which would make the 0.05-stud depth step meaningless
and `ZOffset = slot` the wrong mechanism. The stated fallback — one Part and one SurfaceGui for the
whole hand — does not say how lean and roll become 2D transforms, cannot give each card its own
perspective quad, and would leave the 48 px proof and the hit rects derived from geometry that is
not on screen. **A fan whose layering is wrong is not a fan.** Make the layering check a Wave 0
spike that gates the rest of the plan.

## Worth doing, not blocking

- **F8/F9 — the 47% bound is right but its gate is weak.** The checker derived it in closed form:
  with `scale = clamp(min(W/760, H/350), 0.85, 1.5)`, for `H >= 298` we get `scale <= H/350`, so
  `stripTop/H >= 0.571 - 32/350 = 0.4796`. **0.47 is safe.** But a seat-visibility *report* only
  logs; Phase 4 chose a projected-bounds *assertion* deliberately. As written, pitch -18 and eye
  rise 2.5 could aim at the floor and every test still passes. Add one assertion that the ring-
  adjacent seat anchors project inside the band, or D-44 is unasserted.
- **F5** — the rail caps at `min(count,14)` while `Card.SEAT_STACK_CAP` is 16, so the rail saturates
  before the stacks. Reference the constant.
- **F6** — the ">=2 px per extra card" claim is shown only at the 844x390 reference (2.2 px); at
  scale 0.85 it is 1.7 px. Assert per viewport.
- **F7** — bar colour is ambiguous between `PILE_PANEL` and `TEXT_ON_DARK`; pick one and put it
  under a 3:1 non-text contrast check.
- **F10 — a regression not called out:** the 48 px floor now binds at about fullH 313, so the
  supported floor becomes 360 full-height against Phase 4's 300 safe-height. Say so in the
  disposition table.
- **F11** — the mobile bar is confounded (lobby vs card phase). The real question is whether this
  costs more than the 2D overlay it replaces; add that A/B. **D-54 is not discharged until a named
  device is measured**, which cannot happen overnight.
- **F4** — the prototype geometry is traceable but not reproducible: the Python script is neither
  named nor committed, and the lean pivot and the order of lift/lean/roll are unstated.
- **F12** — selection outline and AFK pulse are both accent and now share the face stroke; state the
  precedence. Selection is still carried by lift and thickness, so D-24 holds.
- **F13** — the inset section never names `WorldToScreenPoint` as the rejected alternative. The
  reason IS given (a pure module cannot call a Roblox API, and the headless 48 px test is worth it),
  just not where a reader looks for it.
- **F14** — set `ResetOnSpawn = false` on the SurfaceGuis.

## Orchestrator's own check of the load-bearing arithmetic

Re-derived independently from the spec's stated inputs, before reading this review: exposed card
width **56.2 px** at 640x360 against the spec's 55.3, and rect height **101.1 px** against its 100
once the 0.4-stud lift is included. The spec is slightly conservative because it accounts for card
tilt. **The >= 48 px guarantee holds with about 15% margin**, so the justification for the phase
survives contact with arithmetic. The checker independently got card height fraction 0.2471 and hit
width ~55.9k. Three derivations agree.
