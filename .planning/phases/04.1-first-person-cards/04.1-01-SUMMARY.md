**Derived, never stored:** arc radius `R = STEP_STUDS / (2 sin(ROLL_STEP_DEG / 2))` = **21.4903
studs**, and the end-slot dip at hand 5 is `R(1 - cos 8°)` = **0.2091 studs = 8.37 design units**. Both
are printed by `config_lock.spec` and by the probe, computed from the constants above.

**Measured IEEE facts, because they change what may be asserted:** `60 * (1/40) == 1.5` and
`16 * (1/40) == 0.4` are **exactly** true, and `1.8 / 2.3 == 72 / 92` is **exactly** true (difference
0.000e+00). But `92 * (1/40)` is `2.3000000000000003` and is **NOT** equal to `2.3`. So `config_lock`
asserts STEP, LIFT and WIDTH as exact products and the card height within an ulp, with the reason in
the file, rather than giving all four a tolerance that would hide which is which.

## Deviations from Plan

### Auto-fixed

**1. [Rule 1 — Bug] `config_lock` pinned `LAYERING_ROUTE` to a literal, so the correct route turned the suite red.**
- **Found during:** Task 3, by running the plan's own mandated mutation 2.
- **Issue:** the new keys were added to the locked-value list wholesale, `LAYERING_ROUTE` among them. With `LAYERING_ROUTE = "Depth"` the whole suite failed — so acting on M-18 would have broken the build, and the plan's promise that a wrong answer costs *one* constant would have been false.
- **Fix:** the value is no longer pinned; its **legality** is asserted instead, and the reason (plus the fact that it was found by mutation) is written into the spec at both the list and the assertion.
- **Files:** `tests/card/config_lock.spec.luau`. **Commit:** `d97de51`.

**2. [Rule 3 — Blocking] `scan.luau`'s argument signature could not run the plan's own verify command.**
- **Issue:** the plan specifies `code-dir <dir> <needle>...` (one directory) and then calls `scan.luau code-dir src scripts DiagonalFieldOfView`, which under that signature means "scan `src` for the needles `scripts` and `DiagonalFieldOfView`" — not what the command reads like, and a needle of `scripts` would be close to vacuous.
- **Fix:** paths and needles are told apart **by the filesystem**: leading arguments that exist (as a directory for the `-dir` modes, as a file otherwise) are paths; everything from the first non-path onward is a needle. An existing path appearing *after* a needle is refused by name rather than silently eaten, because that is the one ambiguity this convention could hide. All five modes accept one or more paths. Documented in the file header under "ARGUMENT SPLITTING, stated because it is a deviation".
- **Files:** `scripts/dev/scan.luau`. **Commit:** `4fddbb4`.

**3. [Rule 3 — Blocking] the probe needed Roblox globals in a file the CI chain type-checks.**
- **Issue:** `scripts/` is type-checked under luau-lsp's **standard** platform, where `game`, `Instance`, `Enum`, `Vector3`, `CFrame`, `Color3` and `UDim2` are unknown globals. Measured: a naive Studio script in `scripts/dev/` produces seven `TypeError: Unknown global` lines and fails the gate.
- **Fix:** every Roblox global arrives through one `getfenv()` table, with an `assert` that names the failure if the file is run outside Studio. `_G` was tried and rejected: selene's `global_usage` lint warns on it, and the house rule forbids a warnings allowance. The result is that the probe is linted, formatted and type-checked like everything else instead of being excluded from the chain.
- **Files:** `scripts/dev/spike-layering.luau`. **Commit:** `4fddbb4`.

**4. [Rule 2 — Missing critical detail] `Brightness` must stay at its default 1 under route Depth.**
- **Found during:** Task 2, re-verifying `SurfaceGui.md` rather than quoting the UI-SPEC.
- **Issue:** the plan's mitigation for route B's lighting cost is `LightInfluence = 0`. The primary page also documents `Brightness` as "the factor by which the SurfaceGui container's light is scaled **when `LightInfluence` is 0**", default 1, with no effect when `AlwaysOnTop` is true. **So `LightInfluence = 0` is necessary but not sufficient under route B:** a non-default `Brightness` would reintroduce exactly the modulation the mitigation exists to rule out.
- **Fix:** recorded in `04.1-LAYERING-DECISION.md` as a named finding, added to the route-diff table, written into **M-23 step 2** as a thing the operator must confirm, and commented at the probe's surface-creation site.
- **Files:** `04.1-LAYERING-DECISION.md`, `MANUAL-CHECKS.md`, `scripts/dev/spike-layering.luau`.

**5. [Rule 1 — Bug] the read-site budget would have been self-contradictory.**
- **Issue:** the plan says "count occurrences of `LAYERING_ROUTE` under `src/`; assert `<= 1`; plan 06 raises it to `== 1`". The **definition** in `Config/Card.luau` is already 1 occurrence in stripped code, so plan 06's carrier would make it 2 and `== 1` could never hold.
- **Fix:** case 3 counts read sites **outside the defining file** — the definition is not a read — and separately asserts the definition's own count is exactly 1 as its non-vacuity check. Both numbers are printed, so the evidence is unambiguous. The header states the ratchet and names plan 06.
- **Files:** `tests/card/layering_contract.spec.luau`. **Commit:** `d97de51`.

## Decided without the owner

The owner was asleep; `AskUserQuestion` was not used. Beyond the five deviations above:

1. **The probe's `VIEW` flag.** Three route groups at the real geometry do not fit one frame at the
   real pose (the hand is 6.5 studs away at 70° vertical FOV). Rather than quietly moving the camera
   back and photographing the wrong scale, the probe takes `VIEW = "A" | "B" | "C" | "ALL"`, in the
   style of M-14's `GREYSCALE` flag: `A`/`B`/`C` sit at the **real** pose with that group centred and
   are the shots the verdict rests on; `ALL` pulls back and **prints that it is an overview only and
   not the real pose**.
2. **The probe builds at y = 400, far above the map.** So the only thing that can occlude a card is
   the probe's own deliberate slab. Building in the lobby would have confused "route B is
   depth-tested" with "the lobby table is in the way".
3. **The probe draws its own minimal face instead of calling `CardFace`.** It judges layering, not
   legibility (that is M-14), so a face-art change cannot alter this photograph and no `CardFace`
   defect can be mistaken for a layering defect. Its colours and font are deliberately **not**
   `CardTheme`'s, for the same reason; every **geometry** number is read from config and none is
   hard-coded, including the 72 x 92 design card, which is derived from `CARD_STUDS` and
   `STUDS_PER_DESIGN_UNIT` rather than retyped.
4. **The probe uses the shipped `PlayerGui` + `Adornee` arrangement, not a SurfaceGui parented to its
   Part.** Draw order is the very thing in question and could depend on where the LayerCollector
   lives, so the convenient edit-mode arrangement would not answer M-18. The probe resolves
   `PlayerGui` at runtime and, in edit mode, falls back to `StarterGui` while **printing that edit
   mode settles nothing**.
5. **`M-12`'s overlay steps 1-3 are kept and marked superseded rather than deleted**, with steps 8-11
   replacing their measurement procedure. A deleted step is a claim nobody can see was ever made.
6. **`config_lock`'s key-count floor is `>= 36`, not an exact count.** The existing case used
   `>= 12`; an exact count would make every future config addition edit this assertion, which is how a
   threshold stops being read. The non-vacuity property wanted here is "the lock ran over enough keys
   to prove something", and a floor says that.
