## `Camera.FieldOfView` — D-43's foundation, confirmed, with a sharpening

> "The `FieldOfView` (FOV) property sets how many degrees in the **vertical** direction the camera
> can view. This property is clamped between `1` and ..."

**So FOV fixes the VERTICAL extent, and horizontal extent varies with aspect ratio.** D-43 said
"fixed FOV makes each card's projected rect a pure function of the viewport", which is true but
under-specified: it is a pure function of the viewport's HEIGHT directly, and of its width only
through the aspect. **D-52's 48 px proof must therefore be driven by the projected card HEIGHT.**
A proof written against width would hold on a 16:9 desktop and fail on a narrower viewport — the
exact shape of bug that passes at the desk and fails on glass.

`Camera.DiagonalFieldOfView` also exists and is documented as the field of view rendering into the
fullscreen area "which may be occluded by notches or screen cutouts on some devices". **Use
`FieldOfView`.** The diagonal one is measured against an area a notch can eat, which is the
opposite of what a 48 px guarantee needs.

## `Camera:WorldToViewportPoint` — the trap

Confirmed signature and purpose: returns the screen location and depth of a world point plus
whether it is on screen. Then, verbatim:

> "This method does not take in account the current GUI inset, such as the space occupied by the
> top bar, meaning that the 2D position returned is taken from the top left corner of the
> viewport. Unless you are using `ScreenGui.IgnoreGuiInset`, this position is not appropriate for
> placing GUI elements."

**This would have broken D-47 silently.** Phase 4's card `ScreenGui` sets `ScreenInsets =
CoreUISafeInsets` deliberately — its own V-24 row — so nothing interactive sits under a notch or
the Roblox top bar (UX-03; M-12 step 3 checks it on a real device). D-47 puts invisible hit buttons
on rects obtained from `WorldToViewportPoint`. **Those two coordinate spaces differ by the inset.**
Every hit target would sit offset from the card the player can see, by the height of the top bar —
small on a desktop, large on a notched phone. It would pass at the reference viewport and fail on
glass.

**The spec must pin one policy and state the consequence for UX-03:**
- (a) the hit layer sets `IgnoreGuiInset = true`, and the geometry keeps targets clear of the
  unsafe area by its own arithmetic; or
- (b) the hit layer keeps `CoreUISafeInsets`, and every projected point has
  `GuiService:GetGuiInset()` subtracted before becoming a rect.

Either is defensible. **Leaving it implicit is not**, and it needs an acceptance test on a
non-zero inset asserting the hit rect and the rendered card coincide — not an eyeball check.

## `ViewportFrame` — if card faces are drawn in one

Documented limits, all relevant to CARD-19 legibility and D-24 greyscale:
- **No shadows and no post-processing** render inside a `ViewportFrame`.
- `Material.Neon` and `Material.Glass` render at the **lowest quality**.
- Lighting behaves as if `EnvironmentSpecularScale` and `EnvironmentDiffuseScale` are **both 0**
  unless a `Sky` child is supplied as a cubemap.

**Two consequences.** First, a face drawn in a `ViewportFrame` is lit flatly by default, which is
GOOD for legibility — the greyscale identity rule wants flat, high-contrast faces, not specular
highlights across a pip. Second, "no post-processing" confirms independently what M-14's probe had
to assume: `ColorCorrectionEffect` cannot be relied on to desaturate card UI, which is why that
probe computes luma itself. That assumption is now evidence.

## Addendum — U1/U2, client-created instances and replication (checked independently)

**The UI researcher reported it could find no explicit doc statement that client-created `Part`s
and `PlayerGui` descendants do not replicate to the server. I checked separately and agree: there
is none.** The `Client-server runtime` page (`/docs/en-us/projects/client-server.md`) describes
replication as the server "constantly updating connected clients", and its only Client -> Server
diagram shows a client that must **tell** the server over a remote in order to affect it. That is
strong implication and is not a statement. Two people have now looked; **do not spend a third
search on it.**

**It does not matter as much as it looks, because the gate the spec specifies is stronger than the
sentence would have been.** D-45 is the phase's largest risk — a card carrying a hidden rank as a
replicated instance would break non-negotiable rule 3 outright — and the spec verifies it by
**probing a live runtime**: an authoritative server and a second client both inspect `Workspace`
and must find no card and no rank. That tests the behaviour the rule cares about, on the engine
version actually shipping, rather than a documented promise about it. A doc sentence would have
been weaker evidence, not stronger.

What a reviewer should insist on, therefore, is not a citation but that the probe is **real**: a
genuine second client, not a stub; an assertion that the probe can FAIL (plant a card with a rank
and watch it fire); and the check repeated in M-11's cheat-client cell, where a hostile client is
already being pointed at the DataModel.

## Addendum 2 — Roblox UI cannot shear, so Route C is a blocker (orchestrator-verified)

**VERIFIED (`GuiObject.md`, 2026-11-10):** `GuiObject.Rotation` is a single `float`. The docs:

> "This property determines the number of degrees by which the `GuiObject` is rotated. Rotation is
> relative to the **center** of the object, **not** the `AnchorPoint`, meaning you cannot change
> the point of rotation."

**There is no shear, no skew and no per-corner transform in vanilla Roblox UI.** Position, size and
one rotation about the centre is the whole 2D transform vocabulary, and D-34 forbids adding a
library to get more.

**Consequence, which the plan correctly draws:** Route C — one SurfaceGui with per-card quads drawn
in 2D — **cannot reproduce a perspective quad**. A card with lean and roll projects to a general
quadrilateral, and a rotated rectangle is not one. So Route C means either drawing corners that are
**not** the corners `Projection` proved — the exact failure D-47 exists to prevent, since the 48 px
guarantee would then describe geometry nobody can see — or commissioning new image assets, which is
not an overnight fallback either.

**So Route C AS SPECIFIED — `Frame`s in one SurfaceGui — is a BLOCKER to raise with the owner, not
a safety net.**

**CORRECTION, 2026-11-10, from the plan check.** An earlier draft of this addendum said that if the
spike rejects both A and B "this phase has no path and must stop". **That was too strong, and the
overstatement was mine.** The no-shear fact rules out `Frame`s; it does not rule out a
**`ViewportFrame` re-rendering the quads through a camera that replicates the locked pose**, which
gives true perspective by actually rendering it rather than by faking it with 2D transforms. This
addendum's own earlier section already records that a `ViewportFrame` is flat-lit by default, which
is the property that keeps the luma floor honest — so it is not obviously a bad route, merely an
unmeasured one (the page gives no cost figure, which is why it was set aside).

**The accurate statement:** if the spike rejects both A and B, the phase stops **for an owner
decision between a `ViewportFrame` route and abandoning the presentation change** — not because no
path exists. That is still the reason to run the spike first and alone, before nine plans of work
rest on an answer nobody has checked.
