<objective>
Write the one rule set. `SpoonPlacement` answers "is this coordinate a valid hiding spot?" with a
single reason, over a baked world built from the `MapContract.Node` snapshot, and the same function
is called by the build-time validator (plan 03-08) and by the hider's live check in Phases 5 and 6.

Purpose: D-04, D-10, D-12, D-13 and HIDE-06. `src/server/core/SpoonPlacement.luau` is the exact
filename `check-guards` already guards as a FOUND-05 no-pay-to-win root, so the guard stops being
hypothetical the moment the file exists. The rule function **takes no avatar argument**, which is
what makes HIDE-07's scale invariance true by construction rather than sampled, and a test asserting
the arity locks it. The rules are evaluated first-match-wins over a locked order, exactly as Phase 2
locked the engine's seven reject codes and the nine `Invariants` violation names.

**The reason order, decided here and locked three ways.** D-12 locks the *rule* order as
in-bounds, standable, reach, line-of-sight, and permits reasons to split a rule. Research left the
names illustrative and left the reach split open. This plan settles it at **six reasons**:

| # | Reason | Rule | Fires when |
|---|--------|------|-----------|
| 1 | `OutOfBounds` | in-bounds | a coordinate is non-finite or outside `Bounds` |
| 2 | `Solid` | standable (a) | the point is inside or within `SPOT_CLEARANCE` of a collidable box |
| 3 | `NoFooting` | standable (b) | no standable cell of ANY region lies within `PICKUP_RANGE` |
| 4 | `OutOfReach` | reach (a) | a cell exists within `PICKUP_RANGE` but none within the effective range `E` |
| 5 | `Unreachable` | reach (b) | a cell lies within `E` but none of them is connected to the seeker spawns |
| 6 | `NoSight` | line-of-sight | among the connected in-reach cells, none has a clear eye segment to the point |

The order is not cosmetic. A spot inside the solid `Core` must report `Solid`, not a downstream
sightline failure — reporting a fundamental failure as a downstream symptom is the most expensive
way for this code to be wrong, which is the same reasoning that put `circulation` (conservation)
before `unsatisfiable` (stall statistics) in `Invariants.check`. `OutOfReach` precedes `Unreachable`
for the same reason: a geometric distance failure is more fundamental than a connectivity failure.

Output: the guarded rule module, the placement corpus that ROADMAP criterion 1 names as a
deliverable, and the signature and config locks.

```luau
--!strict
local MapContract = require("./MapContract")
local Obb = require("./Obb")
local WalkGrid = require("./WalkGrid")

type Vec3 = MapContract.Vec3
type Aabb = MapContract.Aabb
type Node = MapContract.Node

-- The injected config. The KEY NAMES ARE UPPER_SNAKE so src/shared/Config/Placement.luau IS a
-- PlacementConfig with no adapter between them: an adapter would be a second place where CI and
-- the live game could disagree about a number, which is exactly what D-01 exists to prevent.
export type PlacementConfig = {
	GRID_SIZE: number,
	STEP_UP: number,
	MAX_SLOPE_DEGREES: number,
	CAPSULE_RADIUS: number,
	CAPSULE_HEIGHT: number,
	REACH_HEIGHT: number,
	EYE_HEIGHT: number,
	SPOT_CLEARANCE: number,
	PICKUP_RANGE: number,
	PICKUP_MARGIN: number,
}

-- THE ORDER IS LOCKED. Declaration order IS evaluation order, first match wins, exactly one reason
-- per point. Never reorder this to make an assertion pass. The rules are four (D-12: in-bounds,
-- standable, reach, line-of-sight) and the reasons split two of them.
--
-- A spot inside the solid Core must report Solid, NOT a downstream sightline failure. Reporting a
-- fundamental failure as a downstream symptom is the most expensive way for this module to be
-- wrong, which is the same reasoning that put `circulation` before `unsatisfiable` in
-- Invariants.check. OutOfReach precedes Unreachable for the same reason: a geometric distance
-- failure is more fundamental than a connectivity failure.
--
-- This order is recorded in THREE places and all three must agree: this type, the REASON_ORDER
-- array below, and tests/placement/corpus.spec.luau. MapValidator.luau carries the same comment
-- beside its reason-to-issue-code table.
export type Reason = "OutOfBounds" | "Solid" | "NoFooting" | "OutOfReach" | "Unreachable" | "NoSight"

export type Verdict = { ok: boolean, reason: Reason? }

export type BakeFault = {
	kind: "BoundsTooLarge" | "SpawnNoFooting" | "SpawnDisconnected",
	detail: string,
	spawnIndex: number?,
}

export type World = {
	bounds: Aabb,
	boxes: { Obb.Box },
	index: Obb.Index,
	grid: WalkGrid.Grid,
	config: PlacementConfig,
	effectiveRange: number, -- PICKUP_RANGE - PICKUP_MARGIN, derived once at bake time
	counters: WalkGrid.Counters,
}
```


**`check` takes exactly two parameters. This is the arity lock (D-10, vacuous-pass gate 6):
`debug.info(SpoonPlacement.check, "a") == 2`.** No avatar argument, and no config argument — the
world holds the config it was baked with, which is what makes the lock meaningful rather than
decorative. HIDE-07's "placement validity is unaffected by the hider's avatar scale" is then a
structural property: there is nothing in the signature for a scale to enter through.

**`bake` returns `(World?, { BakeFault })`, mirroring `MapValidator.validate`'s
`(issues, spec)` convention exactly: the world is non-nil ONLY when the fault list is empty.**

**`check`'s algorithm, in the locked order. Every acceptance comparison shaves `Obb.GEOM_EPSILON`
and every rejection adds it, so each borderline outcome falls on the rejecting side.**

```
E = world.effectiveRange

1. OutOfBounds: reject unless every component is finite AND inside bounds, written with POSITIVE
   comparisons (`p.x >= min.x and p.x <= max.x`) plus an explicit finite test
   (`v == v and v ~= math.huge and v ~= -math.huge`), the same discipline MapValidator.isInteger
   already uses. A rejection written as `p.x < min.x or p.x > max.x` is FALSE for NaN and lets a
   NaN straight through -- research Pitfall 6, and this is the function a client coordinate reaches
   in Phase 6.
2. Solid: for every box within PICKUP_RANGE of the point (bucket query), if
   Obb.distanceToPoint(box, p) <= SPOT_CLEARANCE + GEOM_EPSILON then Solid.
3. NoFooting: gather cells via WalkGrid.cellsNear(grid, p.x, p.z, PICKUP_RANGE) and keep those whose
   root point (cellH + REACH_HEIGHT) is within PICKUP_RANGE of the point in 3D. If none, NoFooting.
4. OutOfReach: of those, keep the ones within E - GEOM_EPSILON. If none, OutOfReach.
5. Unreachable: of those, keep the ones with region == 1. If none, Unreachable.
6. NoSight: sort the survivors by distance ascending and return ok on the FIRST one whose eye point
   (cellH + EYE_HEIGHT) has no box on the segment to the point, using inflate = GEOM_EPSILON so a
   graze counts as blocked. If every one is blocked, NoSight.
```

Sorting by distance and returning on the first clear sightline is the early exit Pattern 4
describes: about 200 columns at `GRID_SIZE` 1 and `PICKUP_RANGE` 7.
