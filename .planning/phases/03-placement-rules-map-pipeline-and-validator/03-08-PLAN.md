<objective>
Wire the real rules into the build. `MapValidator.validate` takes the placement config, runs
`SpoonPlacement` over every authored default spot after its structural pass, and emits one stable
issue code per failing spot. Both callers — the CI CLI and the runtime loader — inject the shipped
values.

Purpose: MAP-02. *An automated validator runs every authored default spot through the real placement
rules and fails the build on any that would be unfindable.* This is the plan where "the real
placement rules" becomes literally true: the validator calls the same `check` the Phase 5/6 hider
will call, over a world baked by the same `bake`, with the same injected numbers. D-17 is STRICT, so
one failing spot is one issue and any issue fails the build.

**MAP-02 is itself an integrity control, which makes a validator that can be made to pass vacuously
the vulnerability.** The guard against that is the existing convention taken seriously: every new
code gets a fixture asserting the issue set **equals** `{that code}`, not "contains" it, so a
validator that rejected everything or rejected for the wrong reason fails. The one gate that cannot
be tested that way is "the runtime caller uses the shipped values", because `MapLoader` needs the
Roblox API and cannot run headlessly — so it becomes a source assertion over **comment-stripped**
source, since a raw grep that also matches a comment passes vacuously.

**Ordering note.** The placement stage runs only when the structural issue list is empty. That is
not an optimisation: without it the stage would dereference folders the structural pass just
reported missing. It also means a spot outside `Bounds` is already `MAP_OUT_OF_BOUNDS` from the
structural pass, so the `OutOfBounds` reason never fires inside `validate` — it exists for the
runtime hider check in Phase 6, where the point comes from a client.

Output: `validate(root, placement)`, eight new codes each with its own fixture, both call sites
injected, and the comment-stripped source lock on the runtime one.
</objective>

**The reason-to-code table in `MapValidator.luau`. This is the second of the three places the locked
order is recorded, and the comment above it must say so.**

```luau
-- SpoonPlacement.Reason -> stable issue code. The ORDER of the reasons is LOCKED and recorded in
-- THREE places: SpoonPlacement.luau's `Reason` type union, the comment there, and this table plus
-- tests/placement/corpus.spec.luau. Never reorder it to make an assertion pass.
--
--   1 OutOfBounds   in-bounds        -> MAP_OUT_OF_BOUNDS (the structural pass fires first, so this
--                                      row never triggers inside validate; it exists so the mapping
--                                      is TOTAL and a future caller cannot hit a nil code. The
--                                      reason itself is live for the Phase 6 hider check, where the
--                                      point comes from a client.)
--   2 Solid         standable (a)    -> MAP_SPOT_SOLID
--   3 NoFooting     standable (b)    -> MAP_SPOT_NO_FOOTING
--   4 OutOfReach    reach (a)        -> MAP_SPOT_OUT_OF_REACH
--   5 Unreachable   reach (b)        -> MAP_SPOT_UNREACHABLE
--   6 NoSight       line-of-sight    -> MAP_SPOT_NO_SIGHT
--
-- A spot inside the solid Core must report Solid, NOT a downstream sightline failure. Reporting a
-- fundamental failure as a downstream symptom is the most expensive way to be wrong, which is the
-- same reasoning that put `circulation` before `unsatisfiable` in Invariants.check.
local CODE_OF_REASON: { [string]: string } = {
	OutOfBounds = OUT_OF_BOUNDS,
	Solid = SPOT_SOLID,
	NoFooting = SPOT_NO_FOOTING,
	OutOfReach = SPOT_OUT_OF_REACH,
	Unreachable = SPOT_UNREACHABLE,
	NoSight = SPOT_NO_SIGHT,
}
```
