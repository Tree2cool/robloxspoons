<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Studio session to live player data | Once API access is enabled, Studio reads and writes the same data stores as the live game |
| Developer machine to an arbitrary open place | `rojo serve` will sync into whatever place is connected unless restricted |
| Reported configuration to recorded configuration | A setting the owner believes is set but which is not recorded in code leaves the tripwire inert |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-1-10 | Tampering (ASVS V14) | production player data from a Studio session | mitigate | Primary control: a separate dev experience with Studio API access enabled there only and confirmed OFF in production (Task 1, verified in both directions by an actual DataStore write attempt). Secondary: real ids recorded in `Environments.luau` make the `PersistenceMode` `Refuse` branch live (Task 3) |
| T-1-11 | Spoofing | `rojo serve` syncing into the wrong place | mitigate | `servePlaceIds` set to the dev place id, so `rojo serve` refuses any other place (Task 3) |
| T-1-36 | Denial of service (roster) | more than 10 players in a server | mitigate | Production place Maximum Players set to 10 at the platform level (Task 1), behind the already-tested `Admission` kick path |
| T-1-47 | Repudiation | a manual check assumed rather than performed | mitigate | Each box in `MANUAL-CHECKS.md` is ticked only against a reported observation with a date; failures stay unticked with the reason recorded, and `verify.luau` keeps printing unsigned checks on every run (Tasks 2, 3) |
| T-1-48 | Tampering | an inert safety check caused by placeholder values | mitigate | The zero-placeholder case is unit-tested in plan 01-08 to never produce a spurious `Refuse`, and this plan asserts the zeros are gone once the real ids exist (Task 3) |
</threat_model>
