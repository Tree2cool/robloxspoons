<objective>
The anti-ESP decision itself, as a pure function: who may know where a spoon is, this tick.

Purpose: HUNT-02 says *"a seeker learns a spoon's position only while within glint range of it with
clear line of sight"*. D-01 sharpens it into something testable — the server sends `SpoonVisible` on
the **transition into** visibility and `SpoonHidden` on the transition **out**, never a standing list
and never a periodic resend, *"because a list is a map and a resend is a map sampled over time"*.

That makes this file's output a **diff**, not a state, and gives it three properties a spec can pin
hard:

1. **Transition-only.** A stationary seeker in range gets exactly one `SpoonVisible` per spoon over
   100 ticks and nothing more. A resend is a leak with extra steps.
2. **Hysteresis.** Without it, a player standing exactly on the 25-stud edge produces a show and a
   hide every tick — a periodic resend by another name, and the thing D-01 forbids.
3. **The prefilter is provable.** `los` is a dep, so the spec counts its calls and asserts it was
   **never** called for a pair beyond the glint radius. That is the cost argument (research §Cost:
   360 raycasts/s worst case versus 4800/s per-frame) turned into an assertion instead of a comment.

Output: `src/server/core/Visibility.luau` and `tests/hunt/visibility.spec.luau`.
</objective>

```luau
local SpoonRegistry = require("./SpoonRegistry")

export type At = SpoonRegistry.At

export type Cfg = {
	glintRange: number,       -- Hunt.GLINT_RANGE, 25.0
	glintHysteresis: number,  -- Hunt.GLINT_HYSTERESIS, 3.0; leave radius is glintRange + this
	losLossTicks: number,     -- Hunt.LOS_LOSS_TICKS, 2
	eyeFromRoot: number,      -- Placement.EYE_HEIGHT - Placement.REACH_HEIGHT; research F5, M-23
}

-- Written ONCE and exported, so the sweep and its spec ask the same question (the IdleClock.legal
-- precedent). nil in, nil out: a seeker with no character has no eye and sees nothing (Pitfall 9).
function Visibility.eyeOf(root: At?, cfg: Cfg): At?

export type Transition = { userId: number, spoonId: number }

-- `visible[userId][spoonId]` = consecutive ticks the line of sight has been blocked (0 while clear).
-- A key's PRESENCE is the entitlement; the number is only the hysteresis counter.
export type State = { visible: { [number]: { [number]: number } } }
function Visibility.newState(): State

-- `hunterIds` is an ASCENDING ARRAY, not a set: the caller sorts, so the output order is
-- deterministic and a spec can deepEqual it. `spoons` is plan 05-06's unclaimed list, ascending id.
-- Mutates `state`. Publishes NOTHING: the caller publishes what this returns (the IdleClock contract).
function Visibility.step(
	state: State,
	hunterIds: { number },
	spoons: { SpoonRegistry.Spoon },
	eyeOf: (userId: number) -> At?,
	los: (from: At, to: At) -> boolean,
	cfg: Cfg
): ({ Transition }, { Transition })   -- shown, hidden; both ascending by (userId, spoonId)

-- The entitlement question plan 05-12's claim asks. No raycast, no distance: membership only, because
-- membership already encodes range and line of sight to within one tick (research Open Question O8).
function Visibility.sees(state: State, userId: number, spoonId: number): boolean

-- Who currently sees this spoon, ascending. Plan 05-12 publishes SpoonHidden to exactly this set when
-- the spoon is claimed (Pitfall 4), so a stale prompt cannot sit on a taken spoon.
function Visibility.visibleTo(state: State, spoonId: number): { number }

-- A leaver, or a seeker who just claimed and became a spectator. Drops every entry for that user.
function Visibility.forget(state: State, userId: number)
```

**The enter/leave rule, exactly:**

```
enter2 = glintRange ^ 2
leave  = glintRange + glintHysteresis ;  leave2 = leave ^ 2

for each userId in hunterIds:
    eye = eyeOf(userId)
    for each spoon in spoons:
        was = state.visible[userId][spoon.id] ~= nil
        if eye == nil then
            if was then  HIDE  end                 -- Pitfall 9: never a last-known fallback,
            continue                               --            and NEVER call los
        end
        d2 = squared distance (eye, spoon)          -- no sqrt, anywhere
        if not was then
            if d2 <= enter2 and los(eye, spoon) then SHOW; blocked = 0 end
        else
            if d2 > leave2 then
                HIDE                                -- range loss is immediate; hysteresis is the
                                                    -- wider radius, not a delay
            elseif los(eye, spoon) then
                state.visible[userId][spoon.id] = 0 -- reset the blocked counter
            else
                blocked += 1
                if blocked >= losLossTicks then HIDE else store blocked end
            end
        end
```

**Four decisions this plan takes:**

| # | Decision | Why |
|---|---|---|
| 1 | Range loss is **immediate at the wider radius**; only line-of-sight loss is debounced over `losLossTicks` | Two debounces would interact and make the test matrix quadratic for no benefit. Distance is a smooth, monotone quantity — a player cannot cross 3 studs of hysteresis by jitter — whereas line of sight flickers discretely as geometry passes through the ray, which is precisely what needs a debounce |
| 2 | `los` is called **at most once per (hunter, spoon) pair per tick**, and not at all for an out-of-radius pair or a nil eye | The cost argument and the spec's non-vacuity proof both depend on this exact bound: at 10 players and 8 spoons, at most 72 calls per tick and 360 per second |
| 3 | `step` takes `hunterIds` as a **sorted array** supplied by the caller, and sorts its own output | Luau hash iteration order is unspecified. Without this, every transition-ordering assertion in plans 05-09, 05-12 and 05-15 is intermittently red for a reason that has nothing to do with the game |
| 4 | A spoon already in a seeker's visible set still costs one `los` per tick | That is how loss is detected at all. Research notes an optional optimisation (skip the ray when the seeker has moved under 0.25 studs since the last confirmed result) and explicitly does not recommend it yet; do not add it, and do not add LoS caching across ticks |

**What this file must NOT do:** iterate players, iterate spectators, read a claimed spoon (the caller
passes `unclaimed()`), call a clock, publish anything, compute a square root, or implement a second
sight model in Lua geometry. `Obb.segmentHits` stays the validator's; the runtime has exactly one
sight model and it is the injected `los` (research Don't-Hand-Roll: *"two models for the same
question is the CI/live divergence V-18 warned about"*).
