<objective>
The `Claim` intent: one line in the manifest, one bucket, and the deliberate update of three
hard-coded counts in `tests/net/manifest.spec.luau`.

Purpose: `05-DEBT-RECHECK.md`'s V-22 finding pins the claim path. A client-created `ProximityPrompt`
has a `Triggered` that exists **only on that client**, so the documented server pattern
(`prompt.Triggered:Connect(function(player) ... end)`) is **not available to us**. `Claim` is
therefore an ordinary rate-limited manifest intent, exactly like `Draw` and `Pass`, and it rides the
frozen `Gateway` chain unchanged: an unknown intent, a wrong phase, a rate limit and a bad payload
are all rejected before any hunt code runs.

The second half of this plan is the part that is easy to get wrong by accident. `05-PATTERNS.md`
trap 7: `tests/net/manifest.spec.luau` hard-codes `FORBIDDEN_KEYS` (7 names) and `seen == 14`, and
enumerates `Draw` and `Pass` by name in four places. Those counts must be updated **deliberately**,
and the forbidden list must **grow** — because `spoonId` is not in the current list, and a
client-stated position is precisely the thing the server must never trust.

Output: the `Claim` intent, its bucket, and a forbidden-key gate that now also proves a client cannot
send coordinates.
</objective>

**The comment `Claim` must carry in the manifest** (new content, not a copy):
- `spoonId` is an **OPAQUE PER-ROUND ID** produced by a shuffle of `1..N` (plan 05-06). It carries no
  placement information and is not an index into the default-spot list, so guessing an id reveals
  nothing. The server additionally requires that the spoon is in the claimant's **visible set**, so a
  guessed id cannot be claimed at all (plan 05-12).
- The 64 is a **sanity cap, not a game rule** — the cap is 10 players, so at most 8 spoons. The rule
  is the server's `byId` lookup plus the visible-set check, which this bound must never be mistaken
  for.
- There is **no** `pos`, `position`, `x`, `y`, `z`, `time`, `userId`, `seat` or `target` key a client
  could send. `exactKeys` rejects every one as `UnknownKey`. The actor is the `Player` the platform
  hands the server (rule 7) and the position is the server's own
  `HumanoidRootPart` reading (plan 05-14's `positionOf`), never the payload.
- Unlike `Draw`/`Pass` there is **no `seq`**: a claim is not predicted on the client and there is
  nothing to reconcile. A rejected claim sends nothing at all (D-08), so there is no ack to carry.

**The three spec counts, and what they become:**

The five new names are what make the gate prove a client cannot state a position — the single most load-bearing claim in HUNT-01 |

| Threat ID | Category | Component | Disposition | Mitigation Plan |

| T-05-08 | Spoofing | a client claims a spoon by guessing an id | mitigate | Ids are a shuffle of 1..N carrying no placement information (plan 05-06), and plan 05-12 requires visible-set membership, so a guess cannot be claimed even when the id is valid |
