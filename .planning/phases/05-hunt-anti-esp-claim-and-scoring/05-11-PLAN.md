<objective>
The two client view modules a reveal turns into pixels: the local spoon visual with its prompt, and
the remaining-count HUD.

Purpose: D-05 is the decision that makes the client-side prompt possible at all, and the debt
re-check pinned why. *"A prompt that exists only on the client has a `Triggered` event that exists
only on the client. The documented server pattern is not available to us"* — so the affordance is
created **by the owning client on its own local visual**, and the server re-validates every claim.
A server-side `ProximityPrompt`, `Part`, `BillboardGui`, `Attachment` or `*Value` at a spoon position
is HUNT-01 straight through the floor, and PROJECT.md forbids it explicitly.

The second, quieter requirement: **the view must forget.** D-01 says a client learns a position only
while it is entitled to it and forgets it when it is not. A view that kept a `{ id -> position }`
table after `Destroy()` would be a position map sitting in client memory with no entitlement behind
it — technically not an `Instance`, but a cheat client reads memory too. So `hide` clears the entry,
and there is no "last known" anything.

These two modules are **separable and testable by source scan** and have no dependency on the wiring
file, which is why they are their own wave-2 plan: plan 05-13 composes them.

Output: `src/client/ui/SpoonView.luau` and `src/client/ui/RemainingHud.luau`.
</objective>

**Five decisions this plan takes:**

| # | Decision | Why |
|---|---|---|
| 1 | `views[spoonId]` stores the **part only**, and `hide` sets it to `nil` | The part carries the position, so destroying it destroys the record. A parallel `{ id -> {x,y,z} }` table would outlive the entitlement and be a position map in client memory — exactly what D-01's "forgets it when it is not entitled" forbids |
| 2 | `prompt.RequiresLineOfSight = false` | The server already decided entitlement with its own raycast. Double-gating on the *camera's* line of sight would make the prompt unavailable in cases the server considers valid — a silent, unexplainable "the prompt did nothing" for an honest player, and rejections are silent (D-08), so they would have nothing to report |
| 3 | `CanQuery = false` and `CanTouch = false` on the part | It is a visual. A queryable local part would be hit by any future client raycast and could perturb the player's own camera or character collision logic; it also keeps the part out of anything that walks `Workspace` looking for geometry |
| 4 | `show` is **idempotent** | The server sends transitions only (D-01), so a second `show` for a live id should never arrive — but if one did, creating a second part would leave an orphan that `hide` could not destroy, and an undestroyable spoon visual is a permanent false reveal |
| 5 | A single `Folder` under `Workspace`, created in `new` and destroyed in `destroy` | One parent means `hideAll` and `destroy` are each a single operation, and a leftover part after a round is impossible to miss when the folder is empty or gone |

**The A5 fallback, recorded but NOT built:** whether a client-created prompt's touch UI renders and
fires on a phone is assumed, and **M-25** is the check. The fallback is a client-drawn tap button
sending the same `Claim` intent. Do not build it now — build the prompt path, and leave a one-line
comment naming M-25 and the fallback so a failing device session has a decided answer instead of a
redesign.
