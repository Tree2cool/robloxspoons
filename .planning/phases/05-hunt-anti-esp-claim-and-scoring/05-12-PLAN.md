<objective>
The claim, and the round end. Two functions, filled into the marker plan 05-09 left.

Purpose: three distinct hazards converge here and each has a recorded precedent.

**Rule 6, the race.** D-06: a race is decided by first-to-arrive in **one non-yielding server
handler**, with `claimedBy` set synchronously. *"A yield between the check and the write is exactly
how two claimants both win."* Two remote events are delivered to two handler invocations that Roblox
runs one after the other; because the function never yields, the second sees `claimedBy ~= nil`. The
spec drives two `claim` calls back to back with the same `nowDeci` and asserts one winner — **and its
mutation is a variant with an injected yielding hook between the check and the write**, which must
fire.

**D-16 and the Phase 4 bug, in its hunt form.** `RoundEnd` was once published *after*
`table.clear(seated)`, and `toSeated` reads `seated`, so it reached nobody. The hunt's `HuntEnd` is
`toAll`, so it cannot fail that way — but **the scoreboard is built from the very state `finish` then
clears**, so clearing first produces an empty scoreboard delivered successfully. That is the same bug
with a worse failure mode: silent and plausible instead of silent and absent.

**Pitfall 5, re-entrancy.** `RoundLifecycle.isOpen` *ends the round* when the deadline has passed,
and `onEnded` then runs finalisation synchronously. A claim handler that calls `isOpen` and continues
with stale locals can score a claim after the round ended. `false` means return immediately.

Output: `claim` and `finish` in `HuntTable.luau`, plus `tests/hunt/claim.spec.luau` and
`tests/hunt/round_end.spec.luau`.
</objective>

**`claim(userId, spoonId)` — one synchronous function, in exactly this order:**

```luau
local function claim(_self: HuntTable, userId: number, spoonId: number)
	-- Harden first: the Manifest validated, but this core is also driven by specs and by Main's
	-- handler (the Bucket/RejectThrottle precedent).
	assertFiniteInteger(userId, "userId") ; assertFiniteInteger(spoonId, "spoonId")

	-- ARRIVAL TIME, read ONCE (SCORE-02: server arrival time, integer deciseconds, rule 5).
	local nowDeci = deps.nowDeci()

	-- Pitfall 5: isOpen MAY END THE ROUND re-entrantly, which runs finish() synchronously and sets
	-- live = false. Ask once, return immediately on false, and never continue with stale locals.
	if not live then return end
	if not deps.lifecycleOpen() then return end
	if not live then return end                       -- the re-entrant end happened inside the call above

	local hunter = hunters[userId]
	if hunter == nil or hunter.spoonId ~= nil then return end        -- not hunting, or already done
	local spoon = registry:byId(spoonId)
	if spoon == nil or spoon.claimedBy ~= nil then return end        -- gone, or already taken
	-- ENTITLEMENT: you cannot claim what you were never shown. This is what makes a guessed id
	-- useless even when the id is valid (O8: membership already encodes range + line of sight to
	-- within one tick, so there is no second raycast here).
	if not Visibility.sees(vis, userId, spoonId) then return end
	local at = deps.positionOf(userId)                -- NB: not named "pos" (guard R3)
	if at == nil then return end
	if not plaus:reach(at, spoon, deps.walkSpeedOf(userId), deps.rttOf(userId)) then
		deps.onTelemetry("hunt_claim_implausible", { userId = userId, spoonId = spoonId, strikes = plaus:strikes(userId) })
		return                                        -- SILENT to the client (D-08)
	end

	-- Read the audience BEFORE the mutation, because the mutation removes the spoon from every
	-- visible set it is about to be hidden from (Pitfall 4).
	local sawIt = Visibility.visibleTo(vis, spoonId)
	local alsoMine = otherVisibleSpoonIds(userId, spoonId)

	-- ---------------- MUTATION: synchronous, one block, no yield, no publish ----------------
	local ok = registry:claim(spoonId, userId, nowDeci)
	if not ok then return end                         -- belt and braces; the check above already held
	hunter.spoonId = spoonId
	hunters[userId] = nil
	spectators[userId] = true
	ledger:recordFind(userId, spoonId, nowDeci)
	Visibility.forget(vis, userId)
	plaus:forget(userId)
	local remainingNow = registry:remaining()
	-- ---------------- PUBLISH AFTER THE MUTATION ----------------
	publisher.toPlayer(userId, "ClaimOk", { spoonId = spoonId })
	for _, other in sawIt do
		if other ~= userId then
			publisher.toPlayer(other, "SpoonHidden", { id = spoonId })
		end
	end
	for _, id in alsoMine do
		publisher.toPlayer(userId, "SpoonHidden", { id = id })   -- the winner forgets the rest too
	end
	publisher.toPlayer(userId, "Spectate", cfg.bounds)
	publisher.toAll("SpoonsRemaining", { count = remainingNow })
	deps.onTelemetry("hunt_claim_ok", { userId = userId, spoonId = spoonId, deci = nowDeci, remaining = remainingNow })

	-- D-16: LAST, after this claim's own messages, and synchronously.
	if remainingNow == 0 then
		deps.endRound("AllSpoonsClaimed")
	end
end
```

**`finish(reason)` — publish before clear, and the ONE scoreboard publish of the round (D-14):**

D-14 is *"compute per event, publish once"*: a find's points are computed at the instant of arrival,
because that is when the clock reading is correct, and the scoreboard is published **once**, at round
end. `claim` therefore writes a ledger row and publishes no score of any kind — a mid-round score
publish is surface for a wrong number to be seen and remembered, and Phase 6 owns the scoreboard.
The acceptance criteria assert that no `claim` path names `Scoring` or a points value.

```luau
local function finish(_self: HuntTable, reason: string)
	if not live then return end        -- idempotent; RoundLifecycle single-fires but a re-entrant
	live = false                       -- claim during finish must see a closed table
	-- Build from LIVE state. Clearing first would publish a successful, empty, plausible scoreboard
	-- (the Phase 4 RoundEnd bug in its worse form).
	local arrivals: { number? } = {}
	for _, s in registry:placed() do table.insert(arrivals, s.foundDeci) end
	local board = ledger:finalize(cfg.scoring, deps.deadlineDeci(), arrivals, hiderId)
	local payload: HuntRouting.EndPayload = {
		reason = reason, rows = board.rows, hiderId = board.hiderId, hiderScore = board.hiderScore,
	}
	-- Contained: a failed publish must not stop the state reset (the CardService.endRound precedent).
	local told = pcall(function() publisher.toAll("HuntEnd", payload) end)
	if not told then deps.onTelemetry("hunt_end_publish_failed", { rows = #board.rows }) end
	deps.onTelemetry("hunt_ended", { rows = #board.rows, hider = board.hiderId, hiderScore = board.hiderScore })
	-- ONLY NOW
	table.clear(hunters) ; table.clear(spectators)
	vis = Visibility.newState()
end
```

**Six decisions this plan takes:**

| # | Decision | Why |
|---|---|---|
| 1 | The winner is moved to `spectators` and `Visibility.forget` is called **inside** the mutation block | Their round is over (HUNT-07 / D-12) and D-11 says a spectator receives no reveals. Doing it in the mutation rather than after the publish means there is no window in which a sweep could reveal to them |
| 2 | The winner is also sent `SpoonHidden` for **every other spoon they could see** | D-01: a client learns a position only while entitled and forgets it when not. After claiming they are a spectator with no entitlement to anything, so their remaining local visuals must be torn down. Without this, a finisher keeps live prompts on spoons they can no longer take — a position map with no entitlement, and an invitation to call positions out |
| 3 | `Visibility.visibleTo` is read **before** the mutation | `Visibility.forget` and the spoon leaving `unclaimed()` both change who the sweep considers; reading after would fan out to a shrunken or empty set and leave stale prompts on other clients (Pitfall 4) |
| 4 | **No second raycast on claim** (O8) | Visible-set membership already encodes range and line of sight to within one sweep tick, at 5 Hz. A second ray costs a raycast per claim and, worse, creates a second reject path whose timing differs — which is an oracle |
| 5 | `endRound` is called **last**, after `SpoonsRemaining` | D-16 says round end fires immediately and synchronously on the claim that takes the final spoon, *before any scoring publish*. `endRound` runs `finish` synchronously, which publishes `HuntEnd`; so "last" here means the claim's own `ClaimOk`/`SpoonHidden`/`Spectate`/`SpoonsRemaining` reach the wire first, then `HuntEnd`. Any other order would deliver a scoreboard before the message saying the spoon was taken |
| 6 | `finish` sets `live = false` **before** publishing | `RoundLifecycle` already marks the round ended before invoking `onEnded`, so `lifecycleOpen()` is already false — but `finish` is also reachable from a `Timeout` path and from plan 05-14's rollback, and a claim arriving mid-`finish` must see a closed table from this side too. Two independent guards, the `RoundLifecycle` pattern |

**A helper this plan adds:** `otherVisibleSpoonIds(userId, exceptId)` — the ids currently in that
user's visible set other than the claimed one, ascending. Put it beside the claim, not in
`Visibility`, unless plan 05-07's `State` shape makes a one-line `Visibility` accessor cleaner; if it
does, add `Visibility.visibleSpoonsOf(state, userId)` instead and note the change in the summary.
