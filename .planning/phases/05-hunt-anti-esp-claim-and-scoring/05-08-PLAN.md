<objective>
The reach check and the speed sampler: HUNT-08, as arithmetic with injected inputs.

Purpose: D-07 is an unusually careful decision and the reason matters. The rejection threshold is
`PICKUP_RANGE + PICKUP_MARGIN + walkSpeed * rtt`, and that last term is **slack made explicit rather
than fudged**. V-23 says the server-known position of a client-owned character *lags*, so a tight
check would reject honest players on bad connections — and because D-08 makes every rejection
**silent**, an honest player's experience of a false reject is "the prompt did nothing", with no
message, no log they can see, and nothing to report. A too-tight threshold here is the most
user-hostile failure available in this phase.

The other half is the oracle problem. D-08's reason, inherited from Phase 4's D-12: *"a
distinguishable rejection tells a cheat client that its probe was detected, which turns the
anti-cheat into an oracle."* So this file returns a **boolean**, there is exactly one failure
outcome, and the spec asserts that every failing path produces identical (empty) output.

Output: `src/server/core/Plausibility.luau` and `tests/hunt/plausibility.spec.luau`.
</objective>

**The reach rule, exactly:**

```
reach(at, spot, walkSpeed, rtt):
    if at == nil                              -> false     -- no character, no claim
    if any of at.x/y/z, spot.x/y/z, walkSpeed non-finite -> false
    slack  = clampRtt(cfg, rtt) * max(0, walkSpeed)
    limit  = cfg.pickupRange + cfg.pickupMargin + slack
    return distanceSquared(at, spot) <= limit * limit     -- squared both sides; no sqrt

clampRtt(cfg, rtt):
    if rtt is non-finite -> 0                 -- a NaN must NEVER widen the slack
    return math.clamp(rtt, 0, cfg.rttClampSeconds)
```

**The sampler rule, exactly:**

```
sample(userId, at, walkSpeed, nowDeci):
    entry = entries[userId]
    if at == nil              -> entries[userId] = nil ; return   -- no character: no baseline. A
                                                                  -- respawn must not look like a
                                                                  -- teleport.
    if entry == nil           -> entries[userId] = { at, nowDeci, strikes = 0 } ; return
    elapsedDeci = nowDeci - entry.deci
    if elapsedDeci <= 0       -> return                            -- same tick, or a clock that did
                                                                   -- not advance. No judgement.
    -- HORIZONTAL only: vertical is ignored so falls and jumps do not trip it (research A7).
    horizontal = sqrt(dx*dx + dz*dz)
    allowed    = max(0, walkSpeed) * cfg.speedSlack * (elapsedDeci / 10)
    if horizontal > allowed then
        entry.strikes += 1
        if entry.strikes % cfg.strikesToEscalate == 0 then
            onTelemetry("hunt_speed_implausible", { userId = userId, strikes = entry.strikes,
                                                    studs = math.floor(horizontal),
                                                    allowed = math.floor(allowed) })
        end
    end
    entry.at, entry.deci = at, nowDeci       -- the baseline always advances, strike or not
```

**Five decisions this plan takes:**

| # | Decision | Why |
|---|---|---|
| 1 | `reach` returns **false** on a nil or non-finite input rather than erroring | It runs inside plan 05-12's non-yielding claim mutation, where a thrown error would abandon a partially examined claim. Refusing is both safe and, because refusals are silent, indistinguishable from any other refusal — which is exactly the property D-08 wants. The *hardening* errors stay in `sample` and in `new`, where a bad value means a broken caller rather than a departed player |
| 2 | **`clampRtt` is applied inside `reach`,** not by the caller | A caller that forgot it would widen the slack by whatever a laggy client reports. Keeping it inside means the behavioural test (`rtt = 1e6` must still refuse a claim 100 studs away) *is* the gate, with no source scan needed |
| 3 | Escalation fires at **every multiple** of `strikesToEscalate`, not only the first | A single event for a persistent cheater is one log line for an unbounded number of violations; firing every third keeps the signal proportional while the `RejectThrottle`-shaped log throttle in plan 05-14 bounds the console cost |
| 4 | The baseline **always advances**, even on a strike | Otherwise one teleport makes every subsequent sample implausible relative to the old baseline, and a single event becomes an unbounded strike stream — the "one spike reads as a permanent cheater" failure |
| 5 | `sample` takes `walkSpeed` from the caller, which reads it **from the server's `Humanoid`** | Research is explicit: `walkSpeed` is never read from the payload. Recorded here because this file cannot enforce it; plan 05-14's `walkSpeedOf` closure is where it is true and plan 05-17's source scan is where it is checked |

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client-owned character → server-known position | The server's reading lags and the client controls the real one (V-23) |
| server-measured ping → slack | A client cannot forge it but can deliberately raise it |
| refusal → client | Any difference a client can observe between refusal causes is an oracle |
