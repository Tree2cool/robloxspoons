<objective>
The only owner of hidden spoon data in the game: a table of plain records.

Purpose: CLAUDE.md rule 3 says nothing hidden may be a replicated `Instance`. The positive form of
that rule has to live somewhere, and this is it — `{ id, x, y, z, claimedBy, foundDeci }` in a Luau
table inside a pure core, with no `Instance`, no attribute and no `ValueBase` anywhere near it. Every
other HUNT-01 gate in the phase is a check that nothing *else* acquired a copy.

Two details are load-bearing and easy to get wrong:

**The id must be opaque.** If `spoonId` were an index into `mapSpec.defaultSpots`, then a cheat
client that read the map (which it can — the map is in `Workspace`) could turn an id into a position
without ever being in glint range. Ids are a shuffle of `1..N`, and the *choice* of which spots are
used is a separate shuffle. The spec's job is to prove the id order is not the spot order, with a
count showing it looked.

**The registry must not alias the caller's tables.** `CardTable`'s header makes the same rule for
seat specs: *"it must never keep a reference to the caller's table"*, because a map node held in a
pure core is one `table.insert` away from being published.

Output: `src/server/core/SpoonRegistry.luau` and `tests/hunt/registry.spec.luau`.
</objective>

```luau
--!strict
-- src/server/core/SpoonRegistry.luau   (PURE ZONE)
export type At = { x: number, y: number, z: number }

-- The ONE record type for a hidden spoon. `claimedBy` is a userId (not a seat: a seat can be removed,
-- rule 8, but the player is the identity scoring needs). nil means unfound.
export type Spoon = {
	id: number,
	x: number,
	y: number,
	z: number,
	claimedBy: number?,
	foundDeci: number?,
}

export type Registry = {
	-- Chooses `count` spots from `spots` and gives them ids. Errors when count > #spots: a map short
	-- of validated spots is a loud refusal, never a silent short fill.
	autoFill: (self: Registry, spots: { At }, count: number) -> (),
	byId: (self: Registry, id: number) -> Spoon?,
	-- Unclaimed spoons, in ASCENDING ID ORDER. Deterministic so a sweep's output is deterministic.
	unclaimed: (self: Registry) -> { Spoon },
	-- Every placed spoon, ascending id, claimed or not. For round-end finalisation.
	placed: (self: Registry) -> { Spoon },
	remaining: (self: Registry) -> number,
	-- Returns true exactly once per spoon. No publish, no event, no yield: a caller mutation step.
	claim: (self: Registry, id: number, userId: number, nowDeci: number) -> boolean,
}

-- `rng` is an Rng from src/server/engine/Rng.luau, SEEDED BY THE CALLER from a mixed, non-sequential
-- source. This file never seeds one.
function SpoonRegistry.new(rng: any): Registry
```

**Three decisions this plan takes:**

| # | Decision | Why |
|---|---|---|
| 1 | **Two independent shuffles.** One picks which `count` of the `#spots` validated spots are used; the other assigns the ids `1..count` to the chosen spots | A single shuffle would make `id` a permutation of the *chosen* subset, which is still a function of the subset order. Two shuffles make the id carry nothing at all. The cost is one extra `Rng` draw loop |
| 2 | `unclaimed()` and `placed()` return **ascending id order**, and return **copies of the array** (the `Spoon` records themselves are shared, deliberately) | Order first: Luau table iteration order is unspecified, and plan 05-07's visibility sweep iterates this list, so an unordered list makes every transition-ordering assertion in the phase intermittently red. Sharing the records is deliberate — plan 05-12's claim mutates `claimedBy` in place and a deep copy would silently discard the write. Say both halves in the header |
| 3 | `autoFill` is callable **once** per registry; a second call errors | A re-fill mid-round would orphan live `visible` sets keyed by old ids and quietly resurrect claimed spoons. One registry per round, built in `HuntTable.start` |

**Bounds:** `count` is derived by the caller as
`math.max(0, playerCount - Hunt.SPOONS_FEWER_THAN_PLAYERS)`. At the 10-player cap that is 8, which
is why the `Claim` schema's `spoonId` sanity cap of 64 (plan 05-03) is generous rather than tight.
`autoFill(spots, 0)` is legal and leaves `remaining() == 0` — plan 05-12's claim path then has
nothing to claim and plan 05-09's `start` must not call `endRound` on a round that never had a spoon.
Record that as a known edge and leave it to plan 05-09; do not special-case it here.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| map data (client-readable) → spoon id | The map and its default spots are in `Workspace`; a cheat client can read every one |
| caller's tables → pure core state | A retained map node inside a core is one `insert` from a published payload |

| Threat ID | Category | Component | Disposition | Mitigation Plan |
